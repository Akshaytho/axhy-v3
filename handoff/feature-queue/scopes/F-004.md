### Q4 — Did I redesign a human / product concept into a backend-shaped concept?

Audit of round 1 + round 2 + round 3 drafts:

- **Round 1 drift (caught):** "site rules" got re-shaped to "static Site attributes" (name/address/state/workdays) because backend thinking saw `Site` as the obvious source. Plain English: a supervisor's site rules ARE what the supervisor wrote down about this site — i.e., `LivingDoc.siteRules`. Round 1 violated rule 27 by re-shaping the human concept.
- **Round 2 drift (caught):** `recentComplaints` shape re-designed to `{id, text, severity, state, loggedAt}` because the backend's `Complaint` model has those columns and they "felt like" the right summary. Plain English: spec §3.7 line 307 already locked `{id, kind, state, loggedAt, body}`. Round 2 violated rule 27 by reasoning from the backend schema instead of the locked product shape. Also: `siteId` got added to the top-level payload because "the package is per-site so siteId belongs in it" — but spec §3.7 lists 8 fields and `siteId` is NOT one of them (the binding row carries siteId; the package is read in the context of the binding). Round 2 violated rule 27 by adding fields not in the locked shape.
- **Round 3 (this draft):** L3 site rules sourced from `LivingDoc.siteRules` (the supervisor-owned working surface), `recentComplaints` shape matches spec line 307 exactly (with `kind` open question surfaced honestly), `siteId` removed from top-level payload. No backend-shape over-design.

### Q5 — What's the cost model my design implies?

- **HandoffPackage is composed ONCE per binding-create event.** N reads inside one tx (4 reads per pick 5 — siteRules, complaints, activeWorkers, openItems). At Surya's scale (5K employees, ~25 pods, occasional binding churn), this is ~tens of compositions per day, NOT per chat message.
- **No per-message DB queries from F-004.** The package is JSON on the binding row; downstream consumers (chat-context loader, R6 panels) read the JSON, not the source tables.
- **No AI cost.** Composer is pure DB read + projection; no LLM call.
- **The cheaper alternative (load full DB per chat message) is rejected because:** (a) cost explodes — N×messages-per-day×supervisors per day vs once per binding-create; (b) owner explicitly designed the base+delta+live model to prevent this; (c) the audit pain (Ravi Month 9b) is fixed by capturing JUDGEMENT at handoff time, not by re-querying state at chat time.
- **Verified against base+delta+live model:** handoffPackage is the snapshot delivered into the incoming supervisor's BASE on day 1 of new portfolio (or into DELTA on the day of mid-day rebind). Chat-context-loading slice will read this JSON, NOT recompute it.

## 1. Purpose

When HR creates a `SiteSupervisorBinding` — acting cover OR permanent reassignment OR supersession via `reassignPermanentBinding` — F-004 does **two things** depending on the binding's kind:

| Always (acting + permanent)                                                                  | Permanent rebind only                                                                                                                                                                                                                                                                                                                                                                      |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Compose a `HandoffPackage` JSON and write it to `binding.handoffPackage` (frozen, immutable) | Copy outgoing supervisor's site-scoped `LivingDoc.siteRules` entries into the incoming supervisor's `LivingDoc.siteRules` section (preserving `scope.siteId`, provenance noted in `source.pattern`), AND append one "handover from [outgoing] on [date]" summary entry to the incoming supervisor's `LivingDoc.freeNotes`. All writes inside the same Prisma tx as the binding row create. |

**Why the split** (per closure spec §3.7 "Surfaced to" lines):

- **Acting cover:** the binding holder is temporary; merging the outgoing supervisor's site rules into Lakshmi's personal LivingDoc would muddle her context for sites she normally manages. The package shows as a read-only panel on her Today site card — rendered by reading `binding.handoffPackage` directly.
- **Permanent rebind:** Anjali is now the owner of Manikonda. The site-scoped operational rules belong in her LivingDoc going forward (so her own Today site card's SITE RULES panel renders them; so her chat AI context includes them; so subsequent edits land in HER LivingDoc, not stranded in a frozen JSON). The summary entry preserves the handover narrative ("handover from Ravi on 2026-05-16") for audit + personal context.

**Why F-004 cannot punt the LivingDoc-write path:** binding-row-only writes (mechanism X) would mean the existing R6 SITE RULES rendering on site cards (`today.jsx:208-220`, which reads supervisor-own LivingDoc) stays empty for Anjali post-rebind — she'd see the audit-pain "Manikonda has no rules" until the future handoff panel is built. Rule-copy-only (mechanism Y) would lose the handover-narrative metadata. Owner locked mechanism Z (both).

### Q2 — What real runtime pattern do they use?

Three adjacent patterns:

- **Pattern A — Typed audit-emit (`record*`):** Zod-parse typed payload, then write to AuditEvent. F-004 uses this for the new `HANDOFF_PACKAGE_GENERATED` emit (one per binding).
- **Pattern B — Inline compose-into-Json-column:** plain object → `Prisma.InputJsonValue` → set on row create. F-004 uses this for the `handoffPackage:` field on the binding row.
- **Pattern C — LivingDoc upsert + section-array append + version-increment + audit-emit:** chat.ts's existing path for adding a single rule. F-004 reuses this N+1 times on permanent rebind (N = number of outgoing's site-scoped siteRules + 1 handover summary in freeNotes).

### Q3 — Can I extend existing patterns instead of introducing new ones?

Yes. The new `composeHandoffPackage(tx, input)` helper follows pattern B's shape (compose-into-Json-column). The permanent-rebind LivingDoc writes follow pattern C's exact upsert-append-audit shape, called per-rule + once for the summary. The audit emit follows pattern A.

### Q4 — If introducing anything new, why is the old pattern not enough?

Not introducing new patterns. Two refinements that don't change category:

- `composeHandoffPackage` _returns_ the typed payload (so the caller can include it on `tx.siteSupervisorBinding.create` data) rather than writing the audit itself. The audit emit happens at a higher level after the binding row commits.
- The mechanism Z permanent-rebind extension is just orchestration: it loops pattern C N+1 times within the same outer tx.

## 4. Open mechanical details (small, but honest)

These are not blockers. Recommended defaults below; owner may override.

- **Open Q1 — `createdBy` enum fit.** `LivingDocRule.createdBy` enum is `['supervisor', 'ai_inferred']`. Neither literally fits "auto-generated by handover". Default: use `'supervisor'` for both copied rules + summary entry (mechanically Anjali IS the owner going forward; provenance is preserved in `source.pattern`). The audit row gives the real provenance (actorId = the HR user who triggered the rebind, or a SYSTEM_ACTOR_ID for cron-triggered cases). A future schema cleanup could add `'system_handover'` to the enum.
- **Open Q2 — First-ever binding for a site (no outgoing).** Per spec, `outgoingSupervisorId` is NULL. Behavior: `siteRules: []`, `recentComplaints: []` (still query — there may be complaints from a pre-binding period, e.g. bootstrap-seed-time-window edge case; query siteId-scoped regardless), permanent-rebind path's LivingDoc copy loop runs zero iterations, summary entry is still written ("First binding for <siteName> on <date> — no prior supervisor context"). Acting cover on a first-ever binding: ditto, just no LivingDoc writes.
- **Open Q3 — `packageSizeBytes` truncation strategy.** Spec §3.7 **Invariants subsection, line 322** locks the rule verbatim: "Package size capped at a Policy-configurable byte limit (default 100KB); truncation strategy: drop oldest complaints first, then activeWorkers field detail." Code-stage detail (serialize → measure → truncate → re-measure → repeat until under cap); not a scope decision. The 100KB default + drop-order are NOT invented by F-004 — they are spec-locked at the cited line.
- **Open Q4 — Idempotency on permanent-rebind LivingDoc writes.** If `reassignPermanentBinding` is somehow re-invoked for the same site/cutover (replay / retry), we don't want duplicate copied rules in the incoming's LivingDoc. Recommended: F-004 produces idempotent rule IDs (`uuid-v5` derived from binding id + original outgoing rule id), so re-application is a no-op via uniqueness check at write time. Note for code stage.
- **Open Q5 — `kind` field in `ComplaintSummary` (genuine schema gap).** Spec §3.7 line 307 lists `{ id, kind, state, loggedAt, body }` for each complaint summary. The actual `Complaint` model in `packages/shared-schema/prisma/schema.prisma:598-623` has columns `id, companyId, siteId, supervisorId, text, severity, resolvedAt, resolvedBy, createdAt, updatedAt` — **no `kind` column**. Three options for owner to pick: **(a) Constant value** — emit `kind: "site_complaint"` for every entry (truthful: every Complaint today is a site complaint per the schema's `siteId NOT NULL` constraint). **(b) Map from `severity`** — emit `kind: severity.toLowerCase()` (LOW/MEDIUM/HIGH); semantically `kind` would mean "severity tier", which is a stretch of the word "kind". **(c) Schema gap acknowledged — add `Complaint.kind` column** in a separate slice and ship F-004 with `kind: 'site_complaint'` constant as the interim. Recommended: **(c)** if owner wants future complaint categorization (worker-complaint vs site-complaint vs client-complaint), else **(a)** as the simpler default. **(b)** rejected as misleading. Default if no override: **(a)**.
