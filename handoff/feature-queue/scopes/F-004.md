# F-004 Scope — Auto-compose `handoffPackage` JSON at every binding creation

> **Status:** Scope DRAFT pending owner + friend sign-off. No code lands until both sign off. Drafted 2026-05-16 on branch `feat/f-004-handoff-package-composer` (forked from main `edf6172`).

## 1. Purpose (simple English)

When HR creates a binding — acting cover OR permanent reassignment OR supersession via `reassignPermanentBinding` — the incoming supervisor walks in cold. They need site context: how the site operates, what just went wrong (recent complaints), who the workers are, what decisions are still open, what's scheduled in the next week.

The schema already reserves space: `SiteSupervisorBinding.handoffPackage Json?` exists nullable at [packages/shared-schema/prisma/schema.prisma:1051](packages/shared-schema/prisma/schema.prisma#L1051), with a schema comment: "Composer logic lands in a later slice — column is nullable for now." F-004 IS that later slice.

Compose-once-at-write-time means every downstream consumer (R6 "while you were out" digest, F-005 HR portal handoff card, F-007 notification dispatcher payload) reads the same snapshot — no rebuilding, no drift.

### Q2 — What real runtime pattern do they use?

Two patterns are in play in adjacent code:

- **Pattern A — Typed audit-emit (`record*`):** input has a typed `payload`; the helper Zod-parses the payload first, then writes. Used for every `BINDING_*` audit row. Tight schema contract, parse-failures throw at the helper boundary.
- **Pattern B — Inline compose-into-column (`originContext`):** a plain JS object literal composed at the call site, cast to `Prisma.InputJsonValue`, written into a `Json?` column on the row being created. No Zod parse at write time; consumers must defensive-parse.

F-004 sits between the two. The column is `Json?` so technically pattern B works. But the closure spec §3.7 + Decision 8 expect a well-shaped payload that multiple downstream features will consume — pattern A's Zod contract gives us schema discipline that `originContext`'s open shape lacks. Recommended below: **pattern A** — define `HandoffPackagePayloadSchema` in shared-schema and parse it before write.

### Q3 — Can I extend that pattern instead of introducing a new one?

Yes. The composer follows pattern A:

```ts
// apps/backend/src/lib/handoff-package-composer.ts
export type ComposeHandoffPackageInput = {
  companyId: string;
  siteId: string;
  // `at` defaults to new Date(); accepted for test determinism + future-dated reassigns
  at?: Date;
};

export type ComposeHandoffPackageResult = HandoffPackagePayload; // validated Zod object

export async function composeHandoffPackage(
  tx: Prisma.TransactionClient,
  input: ComposeHandoffPackageInput,
): Promise<ComposeHandoffPackageResult> {
  // ... 4 read queries (rules / complaints / workers / open decisions / calendar)
  const payload: HandoffPackagePayload = { ... };
  return HandoffPackagePayloadSchema.parse(payload); // throw on malformed
}
```

Then `reassignPermanentBinding` (and a thin wrapper for plain binding-create, see §5 below) calls `composeHandoffPackage` BEFORE its `tx.siteSupervisorBinding.create({...})` and includes the result as the `handoffPackage:` field on the create data.

### Q4 — If I'm changing the pattern, why is the old one not enough?

Not changing — extending. Two small refinements vs strict pattern A:

- The composer's _result_ is the payload itself (not void). The existing `record*` helpers return void because the audit row IS the side effect; F-004's composer returns the payload because the caller writes it into a binding column. Same Zod-parse-then-return-typed-value discipline.
- The composer doesn't emit an audit row (the binding-create flow already emits `BINDING_CREATED` via `recordBindingCreated`; F-004 just enriches that row's data).

No new pattern category; matches repo reality.

## 4. Open questions surfaced by the rule-26 survey

These are genuine ambiguities that the survey exposed. Recommended defaults given; final lock awaits sign-off.

- **Open Q1 — How is "site rules" composed?** The Site model at [schema.prisma:137-161](packages/shared-schema/prisma/schema.prisma#L137-L161) has NO dedicated rules field. Candidates: `name`, `address`, `state` (14-state SiteState placeholder), `workdays` (e.g. `"MTWTFS_"`). **Default:** compose `siteRules = { name, address, state, workdays }` and add a `_note: "site-rules JSON evolves with later slices"` field for honesty. **Alternative:** defer the `siteRules` component entirely until a richer rules schema lands. Recommended: compose now with what we have.
- **Open Q2 — Worker-targeted PROPOSED decisions: derive site via Worker?** For `kind = MARK_ABSENT | APPROVE_LEAVE | etc.` the `SupervisorDecision.targetId` is a `workerId`, not a `siteId`. To filter "open decisions on this site", we'd need to JOIN through `Worker → Assignment (state=ACTIVE) → siteId`. Use the existing `deriveWorkerPrimarySiteId` helper at [effective-responsibility.ts:145](apps/backend/src/lib/effective-responsibility.ts#L145)? **Default:** yes — same helper, called per candidate decision. Slightly N+1 in worst case; fine at handoff-time scale (few decisions per site). **Alternative:** filter to site-targeted kinds only and skip worker-targeted ones. Recommended: include worker-targeted via the existing helper for completeness.
- **Open Q3 — `CalendarEntry` exclusion is correct?** `CalendarEntry` is per-supervisor at [schema.prisma:251-280](packages/shared-schema/prisma/schema.prisma#L251-L280), not per-site. Excluding it from F-004's "upcoming shifts" component is the right scoping (per-site, not per-supervisor). But: should we ALSO include `CalendarEntry` rows that have been `promotedToKind = 'ASSIGNMENT'` and whose resulting Assignment is on this site? **Default:** no — once promoted, they become `Assignment` rows that pick 5's query already catches. The pre-promotion entries are speculative supervisor notes, not durable site plans. Recommended: stick with pick 5 (Assignment-only).
- **Open Q4 — How big can the JSON get at launch scale?** Closure spec doesn't cap size. A pathological site (100 workers + 90 days of complaints + 50 open decisions + 7 days × 100 shifts) could produce ~50KB JSON. Postgres `jsonb` handles megabytes fine, but downstream consumers should not assume tiny. **Default:** no hard cap in this slice; document in the Zod schema that consumers should expect arrays in the low-100s range. Hard cap only if/when a real consumer is impacted.
