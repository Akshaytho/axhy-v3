## 1. Purpose

Insert a PROPOSED → APPLIED lifecycle between the chat extractor's "decision proposal" and the domain write that the apply currently does directly. Today, when the AI proposes `propose_mark_absent` and the supervisor taps Apply, chat.ts:706 routes straight to `POST /workers/:id/mark-absent`, applying the action without ever creating a `SupervisorDecision` row. F-002 fixes that — every proposed decision lands as a PROPOSED `SupervisorDecision` row first, routable via F-001's `GET /decisions/proposed-for-me`, and only transitions to APPLIED when the responsible supervisor confirms.

## 2. Why now

- **F-001 (the routing read API) just shipped + approved 2026-05-15.** Its `GET /decisions/proposed-for-me` consumes the rows F-002 writes — round-trip ready.
- **Schema is ready.** The `SupervisorDecision` model already has `appliedAt` (PROPOSED/APPLIED discriminator), `originContext` JSONB, `proposedDuringAbsence` Boolean — all landed in migration `20260515_layer_1_core_primitives` (commit `095c766`). No migration in this slice.
- **Largest live workflow gap.** Closure spec §3.2 names the SupervisorDecision lifecycle as the most-load-bearing piece for D17 / D20 / C11 / E21 / E22 / E24. Until F-002 lands, EMPLOYMENT-tier ack gate, undo, dismiss, originContext-across-binding all sit on speculative substrate.

## 3. In-scope (what this slice does)

### 3a. PROPOSED writer — primary change

Modify `apps/backend/src/routes/chat.ts` so that every `propose_*` tool call (mark_absent, leave, swap, termination, create_assignment, etc.) writes a `SupervisorDecision` row inside the same transaction that persists the assistant message. The row's fields:

| Field                   | Source                                                                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `id`                    | UUID — also surfaced in `decisionCardData` so the client can reference it on Apply                                       |
| `companyId`             | request auth                                                                                                             |
| `supervisorId`          | `auth.userId` (the originator)                                                                                           |
| `kind`                  | derived from tool name → enum string (`MARK_ABSENT`, `APPROVE_LEAVE`, `SWAP_WORKER`, `TERMINATE_WORKER`, etc.)           |
| `tier`                  | derived from kind → `NOTE` / `OPERATIONAL` / `PERSONNEL` / `EMPLOYMENT` per closure §3.2                                 |
| `targetId`              | workerId for worker-targeted; siteId for site-targeted; leaveRequestId for leave-driven                                  |
| `payload`               | the tool's parameters (existing `decisionCardData.params`)                                                               |
| `appliedAt`             | NULL (PROPOSED)                                                                                                          |
| `ackRequired`           | `true` iff `tier === 'EMPLOYMENT'`; else `false`                                                                         |
| `originContext`         | open Q (see §7) — best-effort JSON capture from the chat thread at write time                                            |
| `proposedDuringAbsence` | `true` iff the originator's effective binding at time T differs from `auth.userId` (i.e. the originator is on a covered) |

### 3b. APPLY handler — point at the row

Modify `/chat/apply` (chat.ts:673–882) so each branch:

1. Looks up `SupervisorDecision` by id (from the client-supplied reference).
2. Verifies `companyId` matches caller's tenant.
3. Verifies `appliedAt IS NULL` (otherwise: 409 ALREADY_APPLIED).
4. Verifies the caller is the **currently responsible supervisor** for the routed target (via F-001's `getEffectiveResponsibleUserId`) — OR the original `supervisorId` if the kind isn't binding-routable.
5. Inside one transaction: sets `appliedAt = now()`, then performs the existing domain write (mark_absent / leave / swap / termination / etc.).
6. Emits `SUPERVISOR_DECISION_APPLIED` AuditEvent.

### 3c. DISMISS handler — new endpoint

Add `POST /decisions/:id/dismiss` to `apps/backend/src/routes/decisions.ts` (the file F-001 created):

- Verifies tenant + caller is responsible (same predicate as apply).
- Sets a `dismissedAt` + `dismissedReason` column (NEW — requires schema column).
- Emits `SUPERVISOR_DECISION_DISMISSED` AuditEvent.
- **Schema decision needed** (see §7): add `dismissedAt` / `dismissedReason` columns now, or defer dismiss to a follow-up slice?

### 3d. New AuditEvent kinds

Add to `apps/backend/src/lib/audit-event.ts`:

- `SUPERVISOR_DECISION_PROPOSED` — emitted at write
- `SUPERVISOR_DECISION_APPLIED` — emitted at apply
- `SUPERVISOR_DECISION_DISMISSED` — emitted at dismiss (if dismiss is in this slice)

Each gets a typed helper (e.g., `recordSupervisorDecisionProposed`) following the existing `recordPolicyChanged` / `recordMembershipPodAssigned` pattern.

## 4. Out-of-scope (explicitly deferred — friend should confirm)

- **Undo window (30-min UI).** R6 spec mentions a 30-min undo; that's a chat-MVP / UI concern that sits on top of the apply path, not its substrate. Out of scope.
- **Worker-side notification of the decision.** That's F-007 (notification dispatcher). Out of scope.
- **EMPLOYMENT-tier HR ack surface.** That's the HR portal F-005. F-002 writes `ackRequired: true` for EMPLOYMENT-tier — the surface that reads + acks comes later.
- **HandoffPackage composition** on binding change. That's F-004.
- **Backfilling existing chat history.** Pre-F-002 chat turns won't get retroactive `SupervisorDecision` rows. Acceptable since the lifecycle is new.

## 7. Open questions (friend's call before code lands)

### Q1. `originContext` JSON shape

Closure §3 names 4 components: (a) chat excerpt, (b) last 30d decisions about the subject, (c) worker recent attendance + complaint history, (d) originator identity. No Zod schema is pinned.

Options:

- **(a) Define a typed Zod schema now** (in `packages/shared-schema/src/zod/origin-context.ts`) — clean, but requires deciding shape upfront with limited downstream-consumer signal yet.
- **(b) Best-effort capture, document field names in JSDoc, refine schema later** — pragmatic; F-002 ships sooner; the originContext stays semi-structured until F-004 (HandoffPackage composer) or HR portal F-005 actually reads it.

**Default if friend doesn't pick:** (b). Captures `chatExcerpt`, `recentDecisions[]`, `workerRecentActivity[]`, `originatorIdentity` — all optional. F-002 writes them best-effort; consumers can defensive-parse.

### Q2. Scope: PROPOSED-writes only, or include APPLY transition?

The feature-queue entry says both. But that doubles the surface area.

Options:

- **(a) Single slice — PROPOSED + APPLY + DISMISS** (large): closes the lifecycle in one round.
- **(b) Split — F-002a (PROPOSED writer only) + F-002b (apply+dismiss handlers)**: faster review cycles, smaller commits.

**Default if friend doesn't pick:** (a). The apply transition is mechanical once the writer exists and the schema allows it; splitting would re-touch the same code paths.

### Q3. DISMISS support in this slice?

Closure spec mentions DISMISS without schema substrate.

Options:

- **(a) Include in F-002** — add `dismissedAt` + `dismissedReason` columns (1 migration) + endpoint + audit kind.
- **(b) Defer to F-002.5** — pull dismiss into its own micro-slice after F-002 lands.

**Default if friend doesn't pick:** (a). The migration is trivial and consolidates the lifecycle in one approval round.

### Q4. State ENUM column?

Closure §3.2 names PROPOSED / APPLIED / DISMISSED / FAILED / EXPIRED / UNDONE as lifecycle states. Today's discriminator is `appliedAt`. Adding the full enum:

- **(a) Now in F-002** — adds clarity, but requires 4 not-yet-implemented states (FAILED / EXPIRED / UNDONE). Risk of premature shape.
- **(b) Defer** — `appliedAt + dismissedAt` is enough for the slice we're shipping. Convert to ENUM later when FAILED/EXPIRED/UNDONE have concrete triggers.

**Default if friend doesn't pick:** (b). YAGNI; the two-column boolean-ish discriminator is enough for the workflows F-002 + F-001 cover today.

### Q5. `proposedDuringAbsence` detection at write time

The flag should be `true` iff the originator is currently covered by an ACTING binding for the target's site. Detection:

- At write time, derive `siteId` for the target (via `deriveWorkerPrimarySiteId` for worker-targeted; or directly for site-targeted).
- Look up `getEffectiveBinding(tx, {companyId, siteId, at: now})`.
- If the effective binding is ACTING AND `actingForUserId === originatorUserId` → set `proposedDuringAbsence = true`.

This is a small reuse of F-001's helpers. Confidence ~95% on this approach.

**Default if friend doesn't pick:** the approach above; no other reasonable interpretation.
