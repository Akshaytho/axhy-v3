## 1. Purpose

Add a small cron framework for **post-expiry side effects only**. First job: `binding-expire-sweep` emits a `BINDING_ENDED_AUTO` AuditEvent for each `SiteSupervisorBinding` whose `effectiveUntil` has passed and that has not yet been audit-emitted. Future sweeps (decision-expire, flagged-visit-auto-escalate, hr-queue-age-escalation, hr-availability-sweep) and the "while you were out" digest land in later slices on the same framework.

## 2. The re-scope (lock this clearly so it doesn't drift)

**Cron is NOT the source of truth for supervisor switching.** Switching is already correct and time-based via `getEffectiveBinding` at `apps/backend/src/lib/effective-responsibility.ts:62-86` (predicate `effectiveFrom <= at AND (effectiveUntil IS NULL OR effectiveUntil > at) AND endedAt IS NULL` — acting binding falls out the instant `effectiveUntil` passes, no cron needed).

Cron is for the **side-effect side** of an already-completed time-based expiry only. This matches the enterprise pattern in Oracle HCM, SAP SuccessFactors, and Workday: effective-dated records are the source of truth; scheduled batch jobs handle side effects (audit, downstream events, digests, notifications).

## 3. Approach A vs Approach B (considered, B rejected — permanent record)

This comparison is captured here so the question doesn't come back later.

### A — 5-minute polling sweep (CHOSEN)

Cron runs every 5 minutes; queries for expired bindings without a `BINDING_ENDED_AUTO` audit; emits the audit per row (one tx per row).

### B — One-time scheduled trigger per binding (REJECTED for now)

When HR creates a binding with `effectiveUntil = X`, also create a one-shot scheduled job that fires at X. When it fires, emit the audit. Cancel/reschedule on every binding mutation.

### Why B was rejected

1. **Owner's "don't overbuild" rule cuts against B**, not for it. B is the more complex design.
2. **Cost concern doesn't survive scrutiny.** Real polling cost is ~$0.02/month, not a meaningful number.
3. **Even with B, we'd still need A as backstop.** Lost triggers (crashed scheduler, deploy mid-fire) need a safety net. The polling sweep IS the safety net. So B is always "A plus extra coordination on top," never "B instead of A."
4. **Edit/cancel coordination is real complexity.** Our `reassignPermanentBinding` already updates a binding's `effectiveUntil`; A handles that free; B adds coordination cost there and on every future binding-mutation path.
5. **Enterprise pattern for workforce/HR is polling**, not delay-queues. Oracle HCM, SAP SuccessFactors, Workday all use scheduled batch jobs for effective-dated side effects. AWS EventBridge Scheduler / Azure Service Bus are general-purpose primitives used for campaigns/reminders, not HR side effects.

### Upgrade path if needed later

If a future product feature ever needs sub-minute latency on "binding expired" events, the upgrade path is clean: keep the polling sweep as backstop, add a delay-queue optimization on top. The polling sweep is the durable foundation; the trigger system would be an optimization, not a replacement.

## 5. In-scope (what the code slice will do)

- **NEW** `apps/backend/src/jobs/binding-expire-sweep.ts` — the first sweep job. Exports `maybeRunBindingExpireSweep(client, log, now?)` mirroring the `maybeResetAiSpend` signature exactly:
  - in-memory `lastSweepInstant: Date | null` marker, scoped to the module (one per dispatcher process);
  - first-boot path returns early without sweeping (record "now" as the marker, like `maybeResetAiSpend`'s first-boot path);
  - subsequent calls fire iff `now - lastSweepInstant >= 5 min`;
  - per-binding work in its own short transaction (pick 4);
  - emits `BINDING_ENDED_AUTO` AuditEvent per row with the pick-6 payload, gated by the pick-7 audit-existence check.
- **WIRED** `apps/backend/src/dispatcher/index.ts:tick` — add `maybeRunBindingExpireSweep(client, log)` call right next to the existing `maybeResetAiSpend(client, log)` call (line 180). Wrapped in `.catch()` the same way so a sweep failure never breaks the outbox-poll loop. No new HTTP route. No new scheduler.
- **NEW test** `apps/backend/test/binding-expire-sweep.test.ts` — real-DB integration test asserting:
  - sweep emits exactly one `BINDING_ENDED_AUTO` per expired binding without prior audit;
  - re-running the sweep is a no-op (idempotent);
  - sweep does NOT mutate the binding row (`endedAt` stays NULL);
  - sweep does NOT change `getEffectiveBinding` results at any test instant (point-in-time queries unaffected);
  - per-row tx isolation — a single bad row doesn't roll back the others.
- Spec already amended in commit `73375aa` (§3.1 + §10 closure spec) — no further spec work in code slice.
