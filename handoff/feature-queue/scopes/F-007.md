- Resisting the urge to broaden F-007 to "all of §7": Decision 4 specifically calls out worker-side supervisor-change as MANDATORY and the W-1/W-2/W-7 audit pain is the highest-value gap. Other notification kinds (`leave_status`, `replacement_invite`, `flag_alert`, `hr_update`) have existing partial stubs (gupshup stubs in `dispatcher/handlers/gupshup.ts`) and are NOT the immediate audit pain. Real channel adapter wiring (Gupshup, FCM, etc.) is a downstream slice per master plan §G.7.
- Honest framing on coalescing: the coalescing rule from closure §7 is implemented as a "same audience + same supervisor pair + same 60-second window" dedup, NOT a full multi-binding-batch coalescer that handles future-scheduled bindings. The 60-second window is sufficient for the Ravi Month 8a case (one HR session creates all 8 acting windows in seconds) and avoids invented complexity. Wider windows can land later.
- No new product behavior smuggled in. The closure-spec §7 audience rules are quoted verbatim in pick 4. Worker.preferredLanguage default 'hi' is the existing schema default. Channel ordering matches closure §7.

### Q5 — What's the cost model my design implies?

- **Compose at audit-emit time, not at chat-read time.** F-007 runs on the dispatcher tick (existing infra; same pattern as F-003) so per-message cost is zero — the cost is per-binding-event (small).
- **No AI cost.** Notification text is template-rendered, not LLM-generated. The Worker.preferredLanguage column drives template selection.
- **DB cost:** for one supervisor-change event affecting N workers, N Notification rows are written (one per audience-member-channel pair). At Surya scale (5K workers × maybe 0.1 binding changes/day on average = 500 events/day × ~5 workers per site × ~3 channels = ~7500 rows/day) the row volume is modest. Indexes on `(companyId, audienceWorkerId, deliveredAt)` already exist (schema.prisma:955).
- **Subscriber cost:** dispatcher polls outbox; F-007 handlers run inside the same dispatcher process. No new cron, no new worker process.
- **Cheaper alternative considered and rejected:** "store one row per event, fan out at read time." Rejected because (a) Notification table is the canonical record per closure §3.4; (b) per-row delivery tracking REQUIRES per-recipient rows; (c) push notification at read time means push happens minutes/hours after the event — exactly the Suresh audit pain.

## 1. Purpose

When HR creates a binding (acting cover, permanent rebind, or BINDING_ENDED_AUTO fires after `effectiveUntil`), F-004 + F-003 emit AuditEvent rows but **no notification reaches the affected workers or the involved supervisors**. F-007 closes that gap:

1. Subscribe to `HANDOFF_PACKAGE_GENERATED` (F-004) and `BINDING_ENDED_AUTO` (F-003).
2. Resolve audience per closure §7: affected workers (ACTIVE assignment on the site at the event timestamp) + outgoing supervisor + incoming supervisor.
3. Compose plain-language `supervisor_change` notifications, localised to recipient's `preferredLanguage`.
4. Write `Notification` rows for each (audience × channel) pair. `in_app_banner` channel delivers immediately (sets `deliveredAt`); push/SMS/whatsapp_out/email rows are log-stubs that also set `deliveredAt` for observability + worker-app rendering (real channel adapters land in a later slice per master plan §G.7).
5. Emit `WORKER_SUPERVISOR_CHANGE_NOTIFIED` audit per worker notification (closure Decision 4 + §9 audit catalogue).
6. Coalesce multi-binding events for the same (outgoing, incoming) supervisor pair within a 60-second window into ONE notification per audience member.

### Q2 — What real runtime pattern do they use?

Three adjacent patterns:

- **Pattern A — Outbox emit inside the source tx:** the F-002/F-003/F-004 path. Domain row + audit + outbox row all commit together; dispatcher drains async. Used by every existing service helper that needs a side effect. **F-007 round 1 picks this.**
- **Pattern B — Cron subscriber polling AuditEvent:** the F-003 binding-expire-sweep pattern. Lower coupling to producers (F-003/F-004 don't change) at the cost of a polling delay (one dispatcher tick ≈ 2s) and the complexity of "what have I already processed?" tracking via partial unique index.
- **Pattern C — Direct compose at audit-emit time (in-process):** the existing F-004 writer pattern (audit emit + LivingDoc write + handoffPackage write are all done inside `writeHandoffPackage`). For F-007 we'd add a `notifySupervisorChange(tx, ...)` call inside `writeHandoffPackage` directly. Equivalent to Pattern A but bypasses the outbox — synchronous in the source tx.

**Architecture pick:** Pattern A (outbox emit inside the source tx). Reasons:

1. Notification fan-out can be N workers × M channels = many rows; doing it inside the source tx would slow binding-create. The outbox decouples this.
2. Dispatcher already handles retries + quarantine — no new retry logic.
3. Future channel adapters (Gupshup, FCM) plug in as additional handlers without touching F-007's audience resolution.
4. F-002/F-003/F-004 wrote outbox rows for exactly this kind of side effect.

### Q3 — Can I extend existing patterns instead of introducing new ones?

Yes. F-007 reuses:

- `enqueueOutbox` (no change)
- Dispatcher tick + handler registry (one new entry: `notification.supervisor_change`)
- `getEffectiveBinding` (no change — call it with the audit's `effectiveAt` timestamp)
- Existing `Notification` table + Zod schemas (no migration, no Zod change)
- `recordAuditEvent` + typed-helper pattern (one new helper: `recordWorkerSupervisorChangeNotified`)
