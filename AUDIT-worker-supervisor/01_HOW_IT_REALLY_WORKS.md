## S1-supervisor-today (confidence 0.92)

A supervisor opens the Today tab in the mobile app and calls `useTodayQuery()` which fetches `/supervisor/today` (apps/backend/src/routes/supervisor-today.ts:28). The backend route extracts `userId` and `companyId` from the JWT, calls `buildTodayForSupervisor()` (today-service.ts:120), which (1) queries for the supervisor's effective site bindings via `getSitesSupervisedByUser()` (effective-responsibility.ts:172) — this applies the ACTING-over-PERMANENT precedence rule at §5.8; (2) parallel-queries Sites, Assignments, Visits, Attendance, and flagged Visits for those sites bounded by today's IST date (today-service.ts:146-189); (3) derives worker state server-side using `deriveWorkerState()` (today-service.ts:331) which maps Attendance.status and Visit.state to one of {on_site, late, no_show, on_leave, pending} (today-service.ts:23-33); (4) aggregates pulse counters (onSite, late, noShow, pending, flagged) and returns TodayResponse validated by Zod schema (packages/shared-schema/src/zod/today.ts). The mobile app renders the response: UrgencyBanner only when pulse.late > 0 OR pulse.flagged > 0 (UrgencyBanner.tsx), FloorPulse shows the 3 counters (FloorPulse.tsx:2-7), and SiteCard renders collapsed-by-default with tap-to-expand for worker rows (SiteCard.tsx:106-109, R6 locked design). When supervisor taps a worker row, MarkAbsentSheet opens (today.tsx:58-60, 171), supervisor picks a reason chip and taps Confirm absent, which POSTs `/workers/:id/mark-absent` (MarkAbsentSheet.tsx:50). The backend route (workers.ts:38-113) wraps the call in `markAbsentService()` (attendance-service.ts:73-171) which (1) checks the worker exists in caller's company; (2) calls `assertCallerSupervisesWorker()` (supervises-worker.ts, derived from effective-responsibility.ts) to verify the supervisor is the effective responsible user for that worker's primary site — this rejects cross-supervisor marks within the same tenant (Q2=B, workers.ts:78, log at line 84-91); (3) upserts Attendance row (status, reason, payDeductPaise computed from Membership.baseSalaryPaise); (4) records AuditEvent (WORKER_MARKED_ABSENT); (5) enqueues Outbox topics (`hr.worker_absent` and `payroll.recompute` if deduction > 0). On success, the mobile app invalidates the Today query (MarkAbsentSheet.tsx:59), which re-fetches the supervisor's latest state. FlaggedReviewSheet (today.tsx:46, 172) renders for any flagged visits in the response but both Resolve and Reject buttons are currently disabled with intent to wire them in a follow-up (FlaggedReviewSheet.tsx:1-30 comment contradicts actual implementation — buttons are stubbed for "Coming with P1 routing"). Decisions, Activity, Chat, Profile tabs all render as honest R6 shells with "Coming next" messaging per the done-memo scope.

**Data handling / connections:** **Tenant scoping & auth:** All routes require JWT-extracted `userId` and `companyId` from `req.auth` (requireAuth middleware at supervisor-today.ts:28). Query parameters never accept `companyId` from the client — always derived from JWT (supervisor-today.ts:46). Multi-tenant safety test case Q2=B at supervisor-today.test.ts verifies cross-supervisor isolation within same tenant (test scenario 3). **Attendance & deduction:** Mark-absent upserts Attendance row using (workerId, date) as unique key (attendance-service.ts:115-132). Pay deduction (payDeductPaise) is computed from Membership.baseSalaryPaise per ADR-0025 (attendance-service.ts:55-61); stored on Attendance and used for payroll outbox topic. **State derivation:** Worker state (on_site/late/no_show/on_leave/pending) is SINGLE SOURCE OF TRUTH derived server-side in deriveWorkerState() (today-service.ts:331) — never recomputed on client. Visit.state vocabulary is canonical per @axhy/state-machines/visit.ts (12 states); Zod schema at shared-schema/src/zod/today.ts:43 validates client receives only valid enum values. **Site responsibility:** getSitesSupervisedByUser() applies ACTING-over-PERMANENT precedence (effective-responsibility.ts:172, §5.8 responsibility model) via 2-query design: Query A gets this user's candidate bindings; Query B gets all bindings for those sites; JS applies precedence locally. Anti-drift test at supervisor-today.test.ts:4 asserts no N+1 regression. **Outbox & async:** Mark-absent enqueues Outbox topics (hr.worker_absent, payroll.recompute) inside the transaction (attendance-service.ts:148-168). Dispatcher (apps/backend/src/dispatcher/) drains these; MSG91 SMS path and payroll consumer are stubbed (done-memo line 21 marked DEFERRED). **Error handling:** 403 NOT_SUPERVISOR rejection logs caller + effectiveUserId for operator forensics (workers.ts:84-91) but surface stays opaque. 404 WORKER_NOT_FOUND (workers.ts:69-74) returns clean 404 to client.

Mobile groups response rows by section (decisions.tsx:114-124), renders three FlatLists (one per section), and each row renders as DecisionCard (DecisionCard.tsx:277-401). Card checks row.requiresTypedConfirm (for EMPLOYMENT tier TERMINATE_WORKER) or renders server-driven actions[] buttons (line 378-380). **Data handling / connections:** **Connection & Tenanting:** GET /supervisor/decisions wraps buildDecisionsForSupervisor in withTenantContext() (supervisor-decisions.ts:69), ensuring RLS isolation. POST /supervisor/decisions/:id/dismiss uses withTenantContext() wrapper (line 121). All tenant checks verify companyId match. **Auth & Responsibility:** Apply and dismiss decisions gate-keep via isCallerAuthorized() (supervisor-decision-writer.ts:269-301), which checks DECISION_KIND_REGISTRY.routingMode to route by binding (worker-targeted → primary site, site-targeted → site directly, origin-only → original supervisor). Authorization is re-checked at commit time (commitApply, dismissProposedDecision) to catch races. **Audit Trail:** All decision lifecycle writes emit audit events (recordDwiProposed, recordDwiApplied, recordDwiDismissed) inside the same transaction. Auto-sweep dismissals emit DWI_EXPIRED audit events (decisions-service.ts:252-264). **Race Safety:** State transitions use conditional updateMany with WHERE predicates (appliedAt IS NULL AND dismissedAt IS NULL) instead of check-then-act. Concurrent taps are serialized by PostgreSQL row-level locking. **Data Integrity Issues:** (1) Mobile passes empty dismiss body, route fills in synthetic reason '(no reason given)' — audit trail records inaccurate supervisor intent. (2) Idempotency deduplication via Idempotency-Key header is correctly wired for /decisions/:id/apply but mobile's useDismissDecision does not send a key — double-taps on /supervisor/decisions/:id/dismiss could create duplicate dismissals (though router-level idempotency may catch this if configured). (3) No pre-validation of decision payload before forwarding to /chat/apply — malformed rows may cause downstream 400 instead of adapter catching it. **Pagination & Counting:** Cursor is base64 JSON payload of (priority, proposedAt, id) — deterministic ordering prevents overlap/skip across pages. Auto-sweep happens before sources run (line 358) so swept rows never appear in response. Page counts include only this page's rows; pageInfo.totalAcrossPages counts all matching rows before pagination.

## S5-coverage-people-ops (confidence 0.92)

The S5 slice implements supervisor-driven coverage & people-ops operations across 4 major features:

1. **Replacement Invites (F28)**: When a supervisor marks a worker absent or needs cover (apps/backend/src/routes/replacement-invites.ts:1-85), the supervisor picks ONE candidate from their supervised sites via mobile UI (apps/mobile/app/(supervisor)/replacement-picker.tsx:1-1129). The `useTodayQuery()` data is scoped to `getSitesSupervisedByUser()` (apps/backend/src/lib/effective-responsibility.ts:172-249), so only workers from the supervisor's current portfolio appear. The invite sends with a 2-minute TTL; worker accepts/declines which auto-creates a 1-day ACTIVE Assignment (replacement-invite-service.ts:250+) or notifies the supervisor to try someone else. All in one tx with audit + push.

2. **Swap Requests**: Supervisor initiates `POST /swap-requests` (swap-requests.ts:44-124) with two workers + site. The route validates the supervisor is responsible for that site via `getSitesSupervisedByUser()` (line 74-77), then calls `createSwapRequestService()` (swap-request-service.ts:54-137) which creates the SwapRequest in SENT state, emits audit + enqueues Outbox topics for both workers' WhatsApp notifications. The route also implements `POST /swap-requests/:id/decide` (line 148-288) where a receiving supervisor (responsible for the site) can approve/reject, with override option.

3. **Leave Requests (Approval)**: Workers submit leave via `POST /leave-requests` (leave-requests.ts:85-133). Supervisors or HR approve/reject via `POST /leave-requests/:id/approve|reject` (line 136-362). For SUPERVISOR role (line 247-262), the route derives the worker's primary site via `deriveWorkerPrimarySiteId()` (effective-responsibility.ts:282-317) and verifies the supervisor is responsible via `getSitesSupervisedByUser()` (line 252-256) — rejects 403 if not responsible. HR callers pass pod-scope gates (line 165-203) instead. All decisions are race-protected via conditional UPDATE on `state='REQUESTED'` (line 269-277).

4. **Responsibility Model (P1.5)**: Every route that needs "who supervises this site/worker" queries `getSitesSupervisedByUser()` (effective-responsibility.ts:172-249) at read-time. The implementation is a 2-query pattern (lines 178-222): Query A finds the supervisor's own effective bindings; Query B finds all effective bindings for those sites to apply §5.8 precedence (ACTING overrides PERMANENT); local JS applies the precedence rule to return only sites where the supervisor is the winner. `deriveWorkerPrimarySiteId()` uses a 4-tier fallback (effective-at-T ACTIVE assignment, then most-recent ACTIVE, then most-recent any, then null) — no denormalized field on Worker. The `SiteSupervisorBinding` table (schema.prisma:1032+) has `actingForUserId` to discriminate temporary vs permanent; the same-day freeze (same-day-freeze.ts:73-90) enforces no responsibility changes take effect before the next tenant-local midnight. Calendar promotion and assignment creation do NOT gate on responsibility at the write layer; routing is read-time only for open PROPOSED decisions.

5. **Mobile UI**: The replacement picker (replacement-picker.tsx:147-1129) sources candidates from `today.data.workers` (useTodayQuery scope), excludes the original worker, renders a client-side search + candidate list, and stages through pick → confirm → waiting (with live 2-min countdown + 5s polling) → outcome. Sites screen (sites.tsx:126-210) shows all sites from `today.data.sites`, workers-on/due ratio, and flagged indicators — all sourced from the Today API which internally calls `getSitesSupervisedByUser()`.

All data flows are tenant-scoped via `companyId` checks in WHERE clauses + `withTenantContext()` middleware (tenant-context.ts). Audit events fire on every state change (REPLACEMENT_INVITE_SENT, LEAVE_APPROVED, SWAP_REQUEST_SENT, etc.). Outbox enqueues push notifications which a dispatcher handler converts to OneSignal sends (Phase C plumbing; stubbed today).

**Data handling / connections:** **Auth & Tenancy**: Every route requires requireAuth (JWT) + companyId check. withTenantContext wraps Prisma tx to set RLS GUC `current_user_company_id`. Cross-tenant attempts return 404 (no info leak). Supervisor responsibility gates use getSitesSupervisedByUser(companyId, userId), no cross-tenant leaks possible.

**Worker Identity Contract**: LeaveRequest.workerId is Worker.id (schema:524), NOT User.id. The original code at leave-requests.ts:125 comment notes prior bug where code treated workerId as User.id, silently returning null for every HR pod check. Fixed 2026-05-29 via parent brief: now joins Worker → User → Membership to resolve pod. Similar fix applied to leave-requests.ts:175-183 for HR pod gate + line 461-476 for detail-view join.

**Audit Trail**: Every major action emits AuditEvent: REPLACEMENT*INVITE_SENT, LEAVE_APPROVED, LEAVE_REJECTED, SWAP_REQUEST_SENT, SWAP_REQUEST_ACCEPTED/REJECTED, BINDING_CREATED, BINDING_ENDED*\*. Audit rows are append-only (no delete/update). targetId is the entity being decided (LeaveRequest.id, SwapRequest.id, etc.). actorId is the User.id of the decider. Payload is JSONB with full context (names, dates, reasons). This enables full reconstruction of who approved what and when.

**Outbox Pattern**: On every state transition, routes enqueue Outbox topics (push notifications + WhatsApp sends). replacement-invite-service.ts:214-230 creates Notification row; leave-requests.ts:310-323 enqueues Outbox with `worker.leave_approved/rejected` topic; swap-request-service.ts:107-134 enqueues `gupshup.send` topics (one per affected worker). The dispatcher processes these asynchronously; failures are retried per Outbox.nextRetryAt. This decouples the sync route response from notification delivery.

**Race Condition Handling**: (1) LeaveRequest.approve/reject uses conditional UPDATE on `state='REQUESTED'` (updateMany with count check, line 269-277) to catch concurrent deciders; on race, re-read and return actual terminal state (line 281-285). (2) ReplacementInvite.accept/decline/cancel uses conditional UPDATE on `status='PENDING'` (service layer, verify pattern); route layer re-classifies on updatedCount=0. (3) SwapRequest.decide uses findFirst + update pattern (not conditional); potential race if two supervisors decide simultaneously, but SwapRequest design (single initiator + single responder) makes this unlikely in practice. (4) Assignments conflict-check at creation time (expand-one-off helpers + createAssignmentService) to prevent double-booking.

**Data Integrity**: Assignment.validFrom/validUntil are Dates (not DateTimes), so times are lost; shift times are stored separately (shiftStart/shiftEnd strings). LeaveRequest uses fromDate/toDate as ISO date strings, no time component. Attendance uses (workerId, date) as unique key to prevent duplicate attendance records for the same worker-day. Calendar.editableUntil is computed at creation + computed at patch time to enforce 30-day edit window. All timestamp comparisons use ISO strings or native Date objects; timezone-aware comparisons happen at the route layer (same-day-freeze.ts uses tenant timezone for midnight cutoff).

**Notification Delivery**: Push notifications enqueue via Notification table (replacement-invite-service.ts:214-230; leave-requests.ts implicit via Outbox topics); Outbox rows are processed by a dispatcher handler that converts to OneSignal API calls. Today, the dispatcher is stubbed — no actual OneSignal sends. WhatsApp (gupshup.send) topics are also stubbed. This is Phase C plumbing, deferred. Until then, supervisors and workers don't receive real notifications; tests mock dispatcher behavior.

CRITICAL GAP: there is NO POST /hr-updates route for HR admins to create updates—only read/ack by supervisors. There is NO outbox enqueue to trigger push notifications. **Data handling / connections:** Tenant isolation: enforced at route level via requireAuth (JWT extracts companyId) and withTenantContext(prisma, companyId) which scopes all queries to that tenant. Multiple supervisors cannot each ack the same row independently—the second ack overwrites the first (BUG-005). Audit trail: HR_UPDATE_ACKED written inside tx with actorId (supervisor userId), targetId (HRUpdate id), payload (wordCount). Audit uses AuditEvent table per spec. No per-rule tracking at launch (correctly deferred). Error handling: POST acknowledge returns honest error on word count failure (400 VALIDATION_FAILED), not found (404 NOT_FOUND), internal errors (500 INTERNAL). No silent failures. Mobile handles errors gracefully via ackError state. Push notifications: completely unimplemented (BUG-002, BUG-003). When implemented, dispatcher must resolve audience, query push tokens (Device table or similar), and enqueue via notification service (Gupshup push, etc.). Token rotation/expiry on Device not addressed in spec; dispatcher should handle stale tokens gracefully (log, skip).
