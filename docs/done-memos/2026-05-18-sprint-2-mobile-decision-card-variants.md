## 3. Idempotency-Key wire-up confirmation

Every action button mutation goes through one code path:

```ts
// apps/mobile/lib/queries/use-decision-action.ts
const idempotencyKey = generateIdempotencyKey();
return apiFetch<unknown>(action.endpoint, {
  method: action.method,
  body: action.method === 'DELETE' ? undefined : body,
  headers: { 'Idempotency-Key': idempotencyKey },
});
```

- **Per-tap freshness:** `generateIdempotencyKey()` runs inside `mutationFn`, so every tap (including double-tap, retry-tap, after-error-tap) produces a new uuid. A double-tap on Slow 3G fires two parallel requests with the SAME key in flight only if the user double-taps fast enough; React Query's default mutation has no de-dup, BUT Cluster F's backend de-dup table catches it server-side and replays the first response. Net effect: zero duplicate approvals.
- **Same header utility as chat:** `generateIdempotencyKey()` from `lib/idempotency-key.ts` (RN 0.74+ `crypto.randomUUID` with RFC 4122 v4 fallback). One utility, three call sites (chat, decision-action, future surfaces).
- **No client-side de-dup yet:** The brief explicitly says "double-tap on a Slow 3G connection must NOT create duplicate approvals" — this is true today because both taps reach the backend with distinct keys, and backend cluster-F de-dup picks the first one. If founder later wants client-side double-tap suppression (200-ms debounce on the button), it's a 3-line change in `Pressable` `onPress`; intentionally not added today because the server-side guarantee is the load-bearing one.
