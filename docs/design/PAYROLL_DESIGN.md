# AXHY Payroll — Researched Design Blueprint

**Date:** 2026-06-06 · **Source:** parallel web research (Uber/Ola/Rapido + Zoho/RazorpayX/Keka/greytHR/ERPNext) + brain project_payment_is_manual.md + founder confirm 2026-06-06.
**Founder constraints:** monthly salary only · manual mark-paid (method+ref, NO gateway ever) · deductions = editable admin-reviewed line, turn-off-able per company · config-driven so every company adapts · paise ints · India/LOP-native · foundational + hard to change (build proven, not clever).

## Recommendation

Build a three-table payroll ledger — PayRun (per company+period) → Payslip (per worker) → PayslipLine (per money line) — that sits on top of the primitives AXHY already has (Membership.baseSalaryPaise as the salary source, Attendance.payDeductPaise as the per-day LOP fact, the append-only Policy table for per-company config, and AuditEvent for the trail). Salary is monthly-only and copied onto each Payslip at run creation (never read live from Membership), LOP is materialised as an EDITABLE adjustment line the HR/owner reviews — never silently netted — and "paid" is a manual mark with method + reference + disbursedAt and NO gateway, ever. This is the proven Zoho/Keka/greytHR/ERPNext shape (PayRun → salary-slip → earning/deduction lines, DRAFT→APPROVED→PAID with maker-checker, manual payment recording) and all four research dimensions converged on it independently, so it is the low-risk, well-trodden choice rather than a clever one.

Every per-company variation (deductions on/off, base-days basis, rounding, pay-period boundaries, approval required, custom adjustment types, payment methods) lives as dotted-key rows in the existing Policy table under a new `payroll` category, and — critically — a snapshot of the resolved config is frozen onto each PayRun (configSnapshot Json) at creation. That gives you two things at once: a new knob is a new JSON key with a code default (NEVER a migration), and a config change in March can never retroactively rewrite February's run. The whole system honours the founder constraints exactly: monthly salary only, manual mark-paid with hand-recorded reference, deductions visible-and-editable and turn-off-able per company, paise ints throughout, India/LOP-native.

## Default LOP formula

Default LOP = round( (frozen baseSalaryPaise ÷ baseDays) × lopDays ), where baseDays comes from configSnapshot.baseDaysBasis. DEFAULT basis = calendar_days (total days in the period: e.g. ₹30,000 ÷ 30 = ₹1,000/day), default rounding = nearest paisa, HALF_DAY = 0.5 of a day. Configurable bases per tenant: calendar_minus_sundays, fixed_26 (statutory minimum-wage / gratuity convention), fixed_30. Why calendar_days as the DEFAULT rather than fixed-26: Zoho states the formula as salary ÷ days-in-month × LOP-days and hinote.in notes the calendar-day basis is "probably the most widely adopted basis," while fixed-day divisors create a documented inconsistency — the worked-day rate and the not-worked-day rate don't reconcile within a single month — so calendar_days is the safest, most-explainable default, with fixed_26 available for companies on a strict Minimum-Wages/gratuity footing. Citations: https://www.zoho.com/in/payroll/academy/payroll-administration/lop-loss-of-pay.html (formula = monthly salary ÷ working/actual days × LOP days), https://www.hinote.in/base-days-for-monthly-salary-calculation/ (calendar-day basis most widely adopted; Payment of Gratuity Act mandates 26 base days; fixed-day inconsistency warning).

## Per-company config model

Reuse the EXISTING Policy table (append-only, dotted key, JSON value, previousValueSnapshot for rollback, category column) — do NOT build a parallel payroll_config table. Add one category: "payroll". Keys (all with hardcoded code defaults so an unset key Just Works, and adding a future knob = a new key + a default constant, NEVER a migration):

- payroll.deductionsEnabled (bool, default true) — the founder's turn-LOP-off switch; if false, recompute skips all LOP lines entirely.
- payroll.baseDaysBasis (enum: "calendar_days" | "calendar_minus_sundays" | "fixed_26" | "fixed_30", default "calendar_days") — the LOP divisor.
- payroll.payPeriod ({ type: "calendar_month" } | { type: "custom", startDay: 21, endDay: 20 }, default calendar_month).
- payroll.rounding (enum: "floor" | "nearest" | "ceil", default "nearest") — applied to each line, paise.
- payroll.approvalRequired (bool, default true) — if false, DRAFT can go straight to PAID (single-actor small-company mode).
- payroll.lopStatuses (string[], default ["ABSENT_NO_CALL"]) — which Attendance.status values produce LOP; companies that also dock unapproved-leave add "ABSENT_APPROVED_LEAVE".
- payroll.halfDayFactor (number, default 0.5) — LOP weight for HALF_DAY.
- payroll.adjustmentTypes (array of {code,label,sign}, default a small built-in menu: advance recovery, uniform, damage, bonus, arrear) — the per-company custom earning/deduction menu, added WITHOUT code change.
- payroll.paymentMethods (string[], default ["CASH","UPI","BANK","CHEQUE"]).
  Resolution: a PolicyService.resolvePayroll(companyId) merges these keys over the code defaults into one typed object. At PayRun creation that resolved object is FROZEN onto PayRun.configSnapshot, and every downstream computation reads the snapshot — so a knob change never rewrites a past run, and a brand-new knob added in code is simply absent from old snapshots and present (with its default) in new ones. Keep the JSON flat (≤2 levels) so it stays queryable and the snapshot stays small.

## Recompute logic

payroll.recompute(payRunId) — pure, idempotent, DRAFT-only:

1. GUARD: load PayRun. If status != "DRAFT", return no-op immediately (an APPROVED/PAID/VOID run is frozen; attendance edits after approval never reach payroll — HR must create a new off-cycle run). This single guard is what makes the immutability promise real.
2. SCOPE: read PayRun.configSnapshot (never live Policy). Resolve workers in scope = active Memberships with role WORKER/SUPERVISOR in companyId whose employment overlaps [periodStart, periodEnd].
3. Per worker, in ONE transaction with the worker's Attendance rows locked (SELECT ... FOR UPDATE on the period window) to avoid a supervisor editing attendance mid-recompute:
   a. Ensure a Payslip row exists (upsert on (payRunId, workerId)). On first create, FREEZE baseSalaryPaise = Membership.baseSalaryPaise.
   b. SYSTEM lines only — delete-and-reinsert ONLY rows where system=true. Rows where system=false OR editedByUserId IS NOT NULL are NEVER touched. This is the no-clobber rule: any HR hand-edit or override survives every future recompute.
   c. Rebuild SALARY_BASE = frozen baseSalaryPaise (prorated by employment overlap if mid-period join/leave, using baseDaysBasis denominator).
   d. If configSnapshot.deductionsEnabled: aggregate Attendance over the period → count LOP days (status ∈ lopStatuses, HALF_DAY counts halfDayFactor) → lopDays. Compute payableDays = baseDays − lopDays. dailyRate = round(baseSalaryPaise / baseDays, rounding). lopPaise = round(dailyRate × lopDays, rounding). Write ONE LOP_DEDUCTION line (amount = −lopPaise, system=true, sourceRef = {lopDays, baseDays, basis}). If deductionsEnabled=false, emit no LOP line at all.
   e. Recompute denormalised rollups: gross = Σ positive lines, totalDeduct = Σ negative system+manual deduction lines, totalAdjust = Σ manual lines, netPayPaise = Σ all line amounts (signed). Store on Payslip.
4. Roll Payslip totals up to PayRun (workerCount, totalNetPaise, totalDeductPaise).
5. Write AuditEvent PAYRUN_RECOMPUTED (payload: counts + totals delta).
   IDEMPOTENCY: because step 3b deletes+reinserts only system rows and recomputes deterministically from frozen salary + current attendance, running recompute twice yields identical output — no duplicate lines, no drift. Trigger: on PayRun create, and on demand via the recompute route (HR presses 'refresh from attendance'); optionally fanned out via the existing outbox with a dedup key of payRunId so a double-delivered message is a safe no-op.

## Lifecycle

DRAFT → APPROVED → PAID, plus a terminal VOID. Transitions go through one state-machine function (no direct status writes), each writes an AuditEvent, each is gated by role:

- DRAFT: created by HR or owner. Fully mutable. Recompute runs here and ONLY here. HR edits adjustment lines, overrides/waives LOP lines (sets system=false semantics via editedBy), adds ADJUST_EARNING/ADJUST_DEDUCTION lines from the configSnapshot.adjustmentTypes menu.
- APPROVED: requires configSnapshot.approvalRequired (if false, DRAFT may skip straight to PAID). The approver MUST be a different user from createdBy when approvalRequired (maker-checker; single-actor allowed only when a company explicitly relaxes it, and that relaxation is itself audited). On approve we stamp approvedByUserId/approvedAt and FREEZE: no recompute, no line edits, attendance changes no longer flow in. Corrections after this point are a new off-cycle PayRun, never an in-place edit.
- PAID: manual mark by owner (or HR if company allows). Records paymentMethod (∈ configSnapshot.paymentMethods), paymentRef (free-text: UPI txn id / cheque no / 'cash'), markedPaidByUserId, paidRecordedAt. PAID is terminal and immutable — money has moved. A wrong amount is fixed by a VOID + a fresh corrective run or a reversal adjustment line in the next run, NEVER by reopening.
- VOID: a DRAFT or APPROVED run created in error can be voided (terminal, audited). A PAID run cannot be voided — only corrected forward.
  Immutability rules: Payslip.baseSalaryPaise and configSnapshot are frozen at creation; system lines are recompute-owned but only while DRAFT; manual lines are HR-owned and never machine-touched; once APPROVED everything is read-only; once PAID the payment fields lock too. Who can do what: HR creates/recomputes/edits-in-draft; owner approves + marks-paid (HR may, per Policy); SUPER_ADMIN never touches a tenant's payroll numbers. Every transition + every line edit lands in AuditEvent with before/after.

## Prisma models

```prisma
model PayRun {
  id             String   @id @default(uuid()) @db.Uuid
  companyId      String   @db.Uuid
  /// Inclusive pay-period window. For monthly: 1st..last-of-month (or the
  /// custom 21..20 window from configSnapshot.payPeriod). @db.Date so no TZ drift.
  periodStart    DateTime @db.Date
  periodEnd      DateTime @db.Date
  /// DRAFT | APPROVED | PAID | VOID. String not enum so the lifecycle can grow
  /// without a migration (same convention as Visit.state / Attendance.status).
  status         String   @default("DRAFT")
  /// Frozen copy of the resolved payroll Policy config at run-creation time.
  /// Recompute + payslip math read THIS, never live Policy. Immutable for the
  /// life of the run. This is what makes config changes non-retroactive.
  configSnapshot Json
  /// Denormalised rollups (sum of payslip nets) so listing 12 months of runs
  /// never scans PayslipLine. Maintained by recompute while DRAFT.
  workerCount        Int      @default(0)
  totalNetPaise      Int      @default(0)
  totalDeductPaise   Int      @default(0)
  createdByUserId    String   @db.Uuid
  approvedByUserId   String?  @db.Uuid
  approvedAt         DateTime?
  markedPaidByUserId String?  @db.Uuid
  /// When the admin pressed 'mark paid' in AXHY.
  paidRecordedAt     DateTime?
  createdAt          DateTime @default(now())
  updatedAt          DateTime @updatedAt

  company  Company   @relation(fields: [companyId], references: [id], onDelete: Cascade)
  payslips Payslip[]

  /// One run per company per period window. Hard guard against duplicate runs.
  @@unique([companyId, periodStart, periodEnd])
  @@index([companyId, status])
  @@index([companyId, periodStart(sort: Desc)])
  @@schema("axhy")
}

model Payslip {
  id        String @id @default(uuid()) @db.Uuid
  companyId String @db.Uuid
  payRunId  String @db.Uuid
  workerId  String @db.Uuid
  /// FROZEN copy of Membership.baseSalaryPaise at run creation. NEVER read live
  /// — an HR salary edit mid-period must not rewrite an open/closed payslip.
  baseSalaryPaise   Int
  /// Payable days after LOP, and the base-days denominator actually used
  /// (from configSnapshot). Stored for payslip transparency + audit.
  payableDays       Decimal @db.Decimal(6, 2)
  baseDaysUsed      Decimal @db.Decimal(6, 2)
  /// Denormalised rollups = SUM of lines. Recomputed while DRAFT only.
  grossPaise        Int @default(0)
  totalDeductPaise  Int @default(0)
  totalAdjustPaise  Int @default(0)
  netPayPaise       Int @default(0)
  /// Mirrors PayRun.status for fast per-worker queries; authoritative status
  /// is always PayRun.status (a payslip is never paid alone).
  status    String @default("DRAFT")
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  payRun  PayRun         @relation(fields: [payRunId], references: [id], onDelete: Cascade)
  company Company        @relation(fields: [companyId], references: [id], onDelete: Cascade)
  worker  Worker         @relation(fields: [workerId], references: [id], onDelete: Cascade)
  lines   PayslipLine[]

  /// One payslip per worker per run.
  @@unique([payRunId, workerId])
  @@index([companyId, workerId])
  @@index([payRunId])
  @@schema("axhy")
}

model PayslipLine {
  id        String @id @default(uuid()) @db.Uuid
  companyId String @db.Uuid
  payslipId String @db.Uuid
  /// Stable taxonomy string, NOT an enum, so companies add custom types via
  /// Policy without a migration:
  ///   SALARY_BASE      (system, gross)
  ///   LOP_DEDUCTION    (system, derived from Attendance; editable)
  ///   ADJUST_DEDUCTION (manual: advance recovery, uniform cost, damage)
  ///   ADJUST_EARNING   (manual: bonus, arrear, incentive, leave reversal)
  kind      String
  /// Human label shown on the payslip (e.g. "Loss of pay — 3 days", "Diwali bonus").
  label     String
  /// SIGNED paise. + adds to net (earnings), - reduces net (deductions). One
  /// sign convention end-to-end avoids the 'is this positive a deduction?' bug.
  amountPaise Int
  /// true = system-generated by recompute (SALARY_BASE, LOP_DEDUCTION).
  /// false = HR hand-entered. Recompute MUST NOT touch system=false rows.
  system    Boolean @default(true)
  /// For LOP lines: back-ref to the Attendance window that produced it, for
  /// audit + drill-down. NULL for salary base + manual adjustments.
  sourceRef Json?
  /// Set when HR overrides a system LOP line (e.g. waives a day). Once set,
  /// recompute treats the line as locked (manual) and never clobbers it.
  editedByUserId String? @db.Uuid
  editedAt       DateTime?
  createdAt DateTime @default(now())

  payslip Payslip @relation(fields: [payslipId], references: [id], onDelete: Cascade)
  company Company @relation(fields: [companyId], references: [id], onDelete: Cascade)

  @@index([payslipId])
  @@index([companyId, kind])
  @@schema("axhy")
}

// NO new PaymentRecord model in buildNow. Payment is recorded inline on PayRun
// (markedPaidByUserId, paidRecordedAt) + two Policy-free columns added when you
// build mark-paid: paymentMethod String? and paymentRef String? on PayRun. One
// manual payment per run; method ∈ configSnapshot.paymentMethods (CASH|UPI|BANK|
// CHEQUE), reference free-text validated at the route. A separate PaymentRecord
// table is only needed if you later split a run into partial/per-worker payments
// — deferLater, not now. Reusing existing models: Membership (baseSalaryPaise,
// bank fields — owner-edit only, unchanged), Attendance (payDeductPaise — the LOP
// source, unchanged), Policy (all config), AuditEvent (kinds: PAYRUN_CREATED,
// PAYRUN_RECOMPUTED, PAYSLIP_LINE_EDITED, PAYRUN_APPROVED, PAYRUN_MARKED_PAID,
// PAYRUN_VOIDED — payload carries before/after for every edit).
```

## Routes (HR/owner-gated)

- POST /api/payroll/runs — create a DRAFT PayRun for {periodStart,periodEnd}; freezes configSnapshot from PolicyService.resolvePayroll(companyId); enqueues/runs recompute. HR/owner only, companyId-scoped, idempotent on (companyId,periodStart,periodEnd).
- GET /api/payroll/runs — list runs for the company (status, period, totals) for the payroll dashboard; HR/owner only.
- GET /api/payroll/runs/:id — one run with all payslips + lines (the review screen showing gross → editable deductions → net per worker).
- POST /api/payroll/runs/:id/recompute — re-pull from attendance; DRAFT-only, returns 409 otherwise; never clobbers manual lines.
- PATCH /api/payroll/runs/:id/payslips/:payslipId/lines — add/edit/waive an adjustment or override an LOP line (DRAFT-only); sets system=false/editedBy, writes AuditEvent PAYSLIP_LINE_EDITED with before/after.
- POST /api/payroll/runs/:id/approve — DRAFT→APPROVED; enforces maker≠checker when approvalRequired; owner (or HR per Policy); 409 if not DRAFT.
- POST /api/payroll/runs/:id/mark-paid — APPROVED→PAID (or DRAFT→PAID when approvalRequired=false); body {paymentMethod, paymentRef}; method must be in configSnapshot.paymentMethods; owner only; terminal.
- POST /api/payroll/runs/:id/void — DRAFT/APPROVED→VOID (terminal); never on PAID; HR/owner; audited.
- GET /api/payroll/workers/:workerId/history — a worker's past payslips (net, method, ref, date) for the worker-detail screen and dispute resolution.
- GET /api/payroll/runs/:id/export — deferLater: CSV/PDF of the approved run for the accountant; gated same as list. Every route filters WHERE companyId = session.companyId FIRST, Zod-validates the body, and lives behind the HR/owner gate; no `any` in handlers.

## Build NOW

- Three Prisma models: PayRun, Payslip, PayslipLine (+ paymentMethod/paymentRef columns on PayRun), reversible migration with documented rollback, on the axhy schema with companyId-scoped indexes.
- Policy `payroll` category + PolicyService.resolvePayroll(companyId) with hardcoded code defaults for every knob (deductionsEnabled, baseDaysBasis, payPeriod, rounding, approvalRequired, lopStatuses, halfDayFactor, adjustmentTypes, paymentMethods) and configSnapshot freeze at run creation.
- payroll.recompute: DRAFT-only guard, salary-base from frozen Membership salary, LOP from Attendance over the period using the configured basis, system-vs-manual line separation (no-clobber), denormalised rollups, idempotent, attendance rows locked during compute.
- Default LOP = salary ÷ calendar-days × LOP-days, nearest-paisa, HALF_DAY=0.5; deductionsEnabled=false short-circuits all LOP lines (founder turn-off).
- DRAFT→APPROVED→PAID→VOID state machine through one transition function, maker-checker when approvalRequired, every transition + line edit writes AuditEvent with before/after.
- HR/owner-gated routes: create run, list, get-with-lines, recompute, edit/waive line, approve, mark-paid (manual method+ref, NO gateway), void, worker history.
- Real-DB integration tests in a separate \_test file: recompute idempotency (run twice = identical), no-clobber (manual edit survives recompute), deductionsEnabled=false yields zero LOP lines, salary-edit-mid-period doesn't move a frozen payslip, PAID is terminal, cross-tenant isolation (companyId filter).

## Defer later

- CSV/PDF payslip export for the accountant (route stubbed, body deferred).
- Worker-side payslip view in the React Native app (push/SMS with breakdown link) — ship the admin prep layer first; worker visibility is the fast-follow once admins trust the numbers.
- Advance ledger as a proper rolling-balance model (AdvanceLedger with append-only entries + auto-proposed recovery) — v1 handles advances as a manual ADJUST_DEDUCTION line; promote to a ledger when month-end balance tracking actually hurts.
- Statutory deductions (PF/ESI/PT/TDS) — explicitly OFF by default per founder salary-only constraint; the line taxonomy + per-rate Policy keys leave room to add them without a schema change.
- Full-and-final settlement worksheet on termination (leave encashment, advance recovery, pro-rated final month) — name it in scope now, build when first termination needs it; it composes from the same Payslip + line model.
- Off-cycle / correction runs UI beyond plain VOID + new run.
- Per-pod / per-location payroll scoping (optional podId on PayRun) — schema leaves room; not needed until a tenant runs separate payrolls per location.
- PaymentRecord table for partial / per-worker payments — inline PayRun fields suffice while payment is one-shot-per-run.

## Irreversible decisions (defended)

- FREEZE salary onto Payslip.baseSalaryPaise at run creation, never read live Membership. A mid-period salary edit must not silently rewrite an open or paid payslip — the dimension-4 research flags reading live salary as FATAL because old payslips would retroactively change. Right call, defended by https://www.wisemonk.io/blogs/loss-of-pay-lop-in-salary and ERPNext salary-slip practice (https://docs.frappe.io/erpnext/v13/user/manual/en/human-resources/payroll-setup).
- FREEZE the resolved config onto PayRun.configSnapshot; never recompute past runs on a Policy change. ERPNext/Keka snapshot config per slip precisely so a March basis-change can't corrupt February. Defended by https://clefincode.com/blog/global-digital-vibes/en/erpnext-v15-hr-module-detailed-overview-and-deep-dive and the JSONB-config pattern https://medium.com/@richardhightower/jsonb-postgresqls-secret-weapon-for-flexible-data-modeling-cf2f5087168f.
- PAID is terminal — corrections go forward (void + new run, or a reversal line next period), never reopen a paid run. Once cash/UPI has left, reversing in-place destroys the audit trail; every source (Zoho, ADP, immutable-ledger pattern) treats paid payroll as INSERT-only. Defended by https://www.adp.com/resources/articles-and-insights/articles/p/payroll-reconciliation.aspx and https://www.hubifi.com/blog/immutable-audit-log-basics.
- LOP stored as an EDITABLE line derived from Attendance, with a system/manual flag — recompute owns system lines, HR owns manual lines, recompute NEVER clobbers a manual override. Storing LOP as a code-only formula is flagged FATAL because companies need to waive a day ('covered by a teammate'); the editable-line model is the founder's explicit constraint and the proven Zoho/greytHR review-before-finalise pattern. Defended by https://www.zoho.com/in/payroll/academy/payroll-administration/lop-loss-of-pay.html and https://help.keka.com/hc/en-us/articles/41388353533073-Approval-Workflow-Maker-Checker-for-Payroll-Finalisation.
- Default base-days = calendar_days (not fixed_26). hinote.in documents that fixed-day divisors create within-month worked/not-worked inconsistency; calendar_days is the most widely adopted and most explainable, with fixed_26 available for strict minimum-wage tenants. Choosing the wrong default and switching mid-year is the named IRREVERSIBLE pitfall — so we pick the robust default up front and freeze it per run. Defended by https://www.hinote.in/base-days-for-monthly-salary-calculation/.
- NO payment-gateway model, ever — payment is a manual mark with method + free-text reference on the run. Hard-coding this absence (rather than leaving a gateway seam) is correct per the locked founder constraint project_payment_is_manual.md; adding a gateway later would be a deliberate constitutional change, not an accidental one.

## Research appendix (per dimension)

### Gig-platform-payouts: How real platforms structure worker earnings, deductions, payout cycles, and visibility for blue-collar workers in India

Real gig platforms (Uber, Ola, Rapido, Swiggy/Zomato delivery, Urban Company) use a core pattern: base compensation (salary or minimum guarantee) + variable earnings (rides/visits/tasks), settled weekly or fortnightly, with transparent per-settlement breakdowns showing gross, itemized deductions (penalties, advances, incentives), and net payable. India's blue-collar market expects VISIBLE itemization (not silent deductions), monthly or weekly settlement (weekly more common for gig), editable adjustment screens (admin reviews before payment), and company-specific config for deduction types (some skip penalties, some require LOP approval). The critical insight: workers MUST see a line-item breakdown BEFORE money leaves their account — not after. Platforms differ on deduction timing (immediate vs settled-amount), advance ledgers (rolling balance vs one-off), and payout velocity (same-day to next-week). AXHY's manual payment model aligns with real patterns: admin marks workers paid + records reference, but the prep (earning summary + visible adjustments) must ship before handoff to accounting.

**Patterns:** Weekly or fortnightly settlement cycles (most common: every Friday for Uber/Ola drivers in India; monthly increasingly common for salaried roles like Urban Company service professionals); Transparent per-settlement breakdown: gross earnings → itemized deductions → net payable, shown to worker before settlement closes; Dual deduction types: (1) automatic/policy (penalties for low rating, cancellations, app-usage violations) and (2) manual/adjustment (advances repaid, performance bonuses, loss-of-pay for absences); Editable adjustment screen before settlement locks: admin can review, modify penalty amounts, add/remove deductions; audit trail of changes; Advance ledger system: rolling balance (₹X outstanding), not one-off text; auto-proposed deduction on next settlement; worker sees balance in real-time; Regional/city config variation: some markets penalize cancellations ₹50/each, others ₹100; some allow instant cash-out (small fee), others weekly only; Company-level config for deduction policies: some cleaning companies will waive penalties, others apply strict attendance loss-of-pay (LOP), some have different rates per role; PII separation: bank details and salary kept encrypted, editable only by owner via 2-step OTP (not admin/HR via UI); Payroll closure: monthly run that feeds statutory deductions (PF/ESI/PT/TDS) calculated per rule, settles full-and-final on termination (includes leave encashment, advance recovery, gratuity if eligible); Same-worker multi-role handling: worker→supervisor promotion moves salary to new Membership row; old role's settlement history remains immutable; Lost-wage scenario flow: worker marked absent → payDeductPaise logged → admin reviews in payroll-close screen as editable line item → can approve, modify, or waive → visible in worker's settlement breakdown; Notification to worker on settlement: SMS/push with download link to settlement PDF (gross, deductions, net, payment method, reference ID) — worker confirms before accepting payment; Payment reference tracking: admin records 'paid via UPI transfer ID ABC123' or 'cash on hand'; reconciliation against bank/UPI logs weekly or monthly

**Pitfalls:** SILENT DEDUCTIONS: Never auto-net deductions without showing them to admin for review first. Workers lose trust if ₹1000 disappears without explanation. Real pattern: append-only ledger with rolling balance, auto-proposed in payroll UI.; PRO-RATA MID-MONTH MISS: Salary = base/26 × days-worked is non-obvious. If code assumes salary = baseSalaryPaise always, then a worker who joined mid-month gets overpaid. v1 MUST support pro-rata; defer rest (statutory/F&F), but this one can't wait (happens every onboarding day).; PAISE ROUNDING CREEP: ₹1000.50 salary ÷ 26 days = ₹38.48 per day. Sum 26 days back != ₹1000 (paise loss). Real platforms either (1) accumulate remainder, (2) distribute as adjustment to last day, or (3) round UP to avoid worker loss. Pick one, document, audit. Diff ≥₹1 is visible; ≥₹10 suggests a bug.; REVERSIBLE PAYMENTS: Once a settlement is marked SETTLED and money goes out, you can't undo it without a full reversal transaction. Real pattern: DRAFT → APPROVED → SETTLED → (if error) create a REVERSAL settlement. Never UPDATE an existing settlement that's already paid.; STATUTORY CALCULATION TIMING: PF is deducted on the _settlement date_, not the earning date. For a fortnightly settlement spanning 2 months, which month's PF rule applies? Real practice: the month the settlement closes. If settling in July but covering June 20–July 5, apply July PF %. Config this explicitly per tenant.; WORKER OPACITY: If admin can only see/edit settlements in a backend tool (Tally), workers never get a settlement PDF. Real platforms: settlement JSON → PDF → SMS link → worker clicks, sees breakdown, confirms receipt. Absence of worker communication = disengagement and wage-theft allegations. MUST ship.; TERMINATION F&F AMNESIA: Worker terminates; admin marks paid salary only. Doesn't calculate leave encashment, advance recovery, or pro-rata final month. ### india-staff-payroll

Real Indian payroll products (Zoho Payroll, RazorpayX, Keka, greytHR) compute monthly salary via a standardized LOP (loss-of-pay) deduction model tied to attendance. The foundational pattern: base_salary ÷ working_days_in_month × absent_days = payDeduct. Working days are configurable (26 for fixed months, 27 excluding Sundays, or actual calendar days). The pay-run lifecycle is draft → add/review LOP & adjustments → approve → record payment (manually outside the system). Attendance feeds payroll via a cut-off date; deductions are editable before approval. Multi-tenant systems must allow each tenant to configure pay period (calendar month vs custom 21-20 date range), working-day calculation method, and whether deductions are mandatory or optional. AXHY's salary-only + manual-pay model aligns with Indian practice—no payment engine needed, only the deduction computation, draft-review-approve workflow, and audit trail for manual payment recording.

**Patterns:** LOP Deduction Formula: (baseSalaryPaise ÷ workingDaysInMonth) × lopDays = payDeductPaise — universal across Zoho/RazorpayX/Keka/greytHR.; Working Days Calculation: Configurable per tenant: (a) Fixed 26 days (assumes 4–5 Sundays per month), (b) Calendar days minus Sundays (actual workdays in that month), (c) Fixed 30 days (less common, creates month-end inconsistency).; Pay-Run Lifecycle: Create → Lock cut-off date (attendance/leave input deadline) → Review inputs (leaves, LOP, bonuses, adjustments) → Approve (multi-level sign-off) → Release payslips → Record payment (cash/UPI/bank transfer outside system) → Close/Archive.; Attendance Input Window: Closed after cut-off date (typically 1–2 days before pay-run end); late submissions roll into next month. Provisional vs actual: mark-absent creates provisional deduction; supervisor can edit within window; final approval freezes it.; Draft-Review-Approve Workflow: Admin creates pay run (collects attendance, LOP, leaves, ad-hoc adjustments), HR/Finance reviews and can edit line items (deductions, bonuses), designated approver signs off (audit trail captures who/when). Payment recording is separate: admin marks 'paid' with reference (cheque#, UPI txn ID, bank transfer date).; Adjustment Lifecycle: Deductions (LOP, unpaid leave) and additions (bonus, arrear, reversal) are all EDITABLE in draft state until approval. Keka's six-step finalization: (1) leave/attendance approvals, (2) bonuses/salary revisions, (3) salary hold review, (4) reimbursements/ad-hoc, (5) statutory overrides, (6) summary & completion.; Audit Trail / Versioning: Each payslip has a version history; edits pre-approval show old→new values with who/when. Soft-delete pattern: corrected payslips link back to original with reason field. Off-cycle runs (bonuses, corrections, arrears) require second approver.; Multi-Tenant Config Knobs: Each company picks (a) Pay period start/end dates, (b) Working-day calculation method, (c) Statutory deduction handling (optional for salary-only), (d) Whether LOP is mandatory or can be waived, (e) Approval chain depth, (f) Payment method defaults.; Reconciliation / Variance Handling: Pre-approval: Compare payroll vs attendance records; catch clock-in/out mismatches, leaves not synced, supervisor mark-absent conflicts. Post-payment: Verify payment ledger vs approved payslips (budget variance). No mid-cycle re-approval; corrections go off-cycle.; Salary Component Separation: Gross salary = fixed + variable components. For LOP, deduct from gross; statutory taxes/PF calculated post-deduction. Custom structures allow component-wise pro-rating (e.g., HRA × (payable_days/total_days)), not just gross deduction.

**Config knobs:** Working Days Calculation Method: Radio {FIXED_26_DAYS, FIXED_30_DAYS, CALENDAR_MINUS_SUNDAYS, ACTUAL_CALENDAR}. Affects payDeductPaise denominator. DEFAULT: FIXED_26 (common for blue-collar India).; Pay Period Definition: Select {CALENDAR_MONTH} or custom date_range [1–31] for month start/end (e.g., 21–20 for some factories). DEFAULT: Calendar month (1st–last day).; LOP Deduction Mandatory: Bool (toggle). If FALSE, allow admin to opt-out of deduction for specific worker for a month. DEFAULT: TRUE (most companies mandate it).; LOP Deduction Source: Enum {GROSS_SALARY, BASIC_SALARY}. For multi-component salary, choose whether to deduct from entire gross or only basic. DEFAULT: GROSS.; Attendance Cut-Off Days Before End: Int (1–7). Deadline for mark-absent/leave-approval relative to pay-period end. DEFAULT: 2 days.; Paid Leave Handling: Enum {AUTO_INCLUDE_IN_WORKING_DAYS, EXCLUDE}. If INCLUDE, public holidays + leaves don't reduce working-day count; if EXCLUDE, paid leave counts as a worked day. DEFAULT: AUTO_INCLUDE.; Half-Day Treatment: Bool. If TRUE, two half-days = 1 LOP day; if FALSE, half-day = 0.5 deduction. DEFAULT: FALSE (some companies don't count half-day as worked).; Approval Chain: Array of User IDs / roles. Maker (creator), Checker (reviewer), Approver (final sign-off). Can be same person (single-approver mode) or different. DEFAULT: 2-step (maker + approver).; Salary Revision Window: Date range for retroactive salary changes in a pay run (e.g., ±7 days after approval). DEFAULT: None (locked after approval to prevent fraud).; Off-Cycle Runs: Bool toggle to enable bonus/correction runs outside main cycle. If enabled, require second approver. DEFAULT: TRUE (required for arrears, corrections).; Manual Payment Recording Options: Enum {CASH, UPI, BANK_TRANSFER, CHEQUE} or multiselect. Store payment_reference field (txn ID, cheque number, bank advice date). DEFAULT: all methods allowed.; Include Statutory Deductions: Bool. If FALSE (salary-only mode, no PF/ESI), skip statutory calculations. AXHY: FALSE.; Currency / Paise Handling: Store all monetary fields as Paise (100 paise = 1 INR). Formatting/rounding rule: ROUND_DOWN or ROUND_NEAREST. DEFAULT: ROUND_DOWN (standard in India for salary).

**Pitfalls:** Immutable Pay-Run Fields: Once approved, do NOT allow editing of baseSalaryPaise or working-days config for that month. Create an off-cycle correction instead. Changing these retroactively breaks audit trail and compliance.; Attendance Cut-Off Enforcement: Hard-close the mark-absent window at cut-off datetime; no backdating after that. Violations should log and fail with clear error. Missing this allows supervisors to adjust payroll after approval (fraud risk).; Pro-Rata Confusion (Fixed 26 vs Actual): If using FIXED_26 days/month, you must NOT pro-rate salary for mid-month joiners (hire date in month). Instead, create a separate salary adjustment or use CUSTOM structures. Using FIXED_26 then pro-rating creates double-deduction.; Public Holiday vs Paid Leave: If a public holiday falls on a non-working day (e.g., Sunday in India), don't count it as a work day (avoid false working-day inflation). Similarly, don't double-count a public holiday that's also marked as paid leave.; Half-Day and Fractional LOP: Rounding errors cascade. If system allows 0.5-day LOP, ensure database stores Decimal, not Int. Use ROUND_DOWN (floor) not banker's rounding, per Indian statutory practice.; Overtime / Extra Shift Not in Working Days: If an employee works extra on Sunday (a non-working day), do NOT add it to working-days count; instead, use overtime/incentive components separately. Conflating them breaks LOP calculation.; Salary Hold / Absconding Flag: Some systems have a 'salary on hold' status (employee absconded, under investigation). If set, MUST NOT process payroll for that month until cleared. Keka Step 3 enforces this; missing it pays salary to absent employee.; Approval Chain Bypass: Never allow a single person to be both maker and approver in a high-value run. Require explicit role separation in config; if relaxed for small companies, log it as a manual override audit event.; Payment Reference Mutability: Once payment is recorded, do NOT allow editing of payment_reference or payment_method without logging a reversal reason. Changing it retroactively (e.g., wrong cheque number) hides fraud.; Multi-Currency / Paise Precision: India uses Paise (1 INR = 100 paise). Never use float; always Int Paise. Rounding mid-calculation (e.g., payDeductPaise = (salary / days) \* lop_days) must use ROUND_DOWN to avoid over-deduction.; Backwards Compatibility of Config Changes: If a company switches working-day method mid-year, old pay runs must stay frozen with old method; only new runs use new config. Retroactive config changes corrupt historical payroll.; Leave Absence Sync Latency: If attendance is auto-synced from HR leave module, mark attendance as PROVISIONAL until manual supervisor confirmation. Don't auto-deduct LOP until confirmed; this avoids double-deduction if leave is rejected later.; Payslip Correction Without Reversal: Some systems allow 'corrected payslip' which replaces the old one. This hides payment overage/shortage. Always use: (old payslip) → VOID → (correction off-cycle) → (new payslip). Chain audit trail.; Tax/Statutory Deduction Freeze: After approval, if company enables statutory (PF, TDS, ESI), do NOT recalculate based on updated gross. Use frozen gross-at-approval-time. Re-calculating opens compliance gaps if external tax rates changed.; No Deduction for Pending Approvals: If a leave is PENDING approval when pay run is finalized, do NOT deduct it. Only finalized APPROVED or REJECTED leaves feed payroll. Pending = treated as PRESENT until decided.; Variant: Rounding Convention Mismatch\*\*: Two companies in same platform may disagree on rounding (one uses ROUND_NEAREST, one ROUND_DOWN). Document in config; audit can fail if inconsistent. Default ROUND_DOWN per India statutory practice.

### attendance-to-pay-calc

Indian blue-collar monthly salary systems convert daily attendance into pay via LOP (Loss of Pay) deductions. Standard formula: Daily Rate = Monthly Salary ÷ Base Days, then multiply by LOP days. Base days can be 26 (minimum wage standard, accounts for 6-day week + 1 rest day) or 30 (calendar days, common in payroll software). The 26-day standard is legally compliant per Minimum Wages Act 1948 and used across states for minimum wage calculations, pro-rata calculations (mid-month joins/exits), and blue-collar workers in cleaning, manufacturing, BPO. Paid leave does not reduce salary; unpaid leave (LOP) or unauthorized absences do. Half-days are 50% of daily rate. All calculations must round to paise (₹/100) consistently. Most production payroll systems (Zoho, RazorpayX, GreytHR) allow attendance deductions to be editable through an admin review/approval workflow before payroll finalization, supporting the founder constraint that deductions must be "EDITABLE adjustment the admin reviews."

**Patterns:** LOP Deduction Formula: (Monthly Salary ÷ Base Days) × LOP Days — works bidirectionally (deduct for absence, restore if marked present); 26-Day Standard for Blue-Collar: Minimum wage law baseline; reflects six-day workweek with one paid weekly rest. Used for: minimum wage compliance, pro-rata joins/exits, LOP calculations across Indian states; 30-Day (Calendar) Alternative: Simplest method; used when company policy opts not to exclude weekends. Monthly Salary ÷ 30 = daily rate. Creates month-to-month variation but easier to explain; Half-Day Handling: 50% of daily rate; applied for late arrivals >15–30 min or early departures; defined in company HR policy; Paid vs Unpaid Leave Distinction: Approved leave (sick, casual, earned) = full salary, no LOP; unapproved/exhausted balance = LOP deduction applied; Editable Deductions (Admin Review): Real systems (Zoho, RazorpayX, GreytHR) store computed LOP on Attendance row, surfaced to HR/admin dashboard for correction BEFORE payroll run finishes. Idempotent: re-marking same day updates status + deduction in one atomic transaction; Pro-Rata Calculation: (Monthly Salary ÷ Base Days) × Days Worked — used for mid-month joins or exits; rounding must be consistent to paise; Mid-Month Join/Exit: Calculate from actual start/end date, include holidays/approved leave in numerator if entitled; Rounding Convention: To nearest paise (₹0.01); SAP / production systems use 'recovery of rounded off amounts' feature to track paise remainder. No legal requirement to round up or down, but must be consistent and transparent; Benefits Impact: EPF (12% of basic + DA), ESI (0.75–3.25% of gross), and gratuity all reduce when LOP reduces monthly salary. Bonus and incentives may be pro-rated by attendance; State/Region Variations: 22–26 working days per month across states (Delhi, Maharashtra, Karnataka, UP all notify minimum wages on 26-day basis). Some sectors use 22 (exclude Sunday + Saturday), some use 26 (6-day workweek)

**Config knobs:** payroll.baseWorkingDaysPerMonth: Enum [26, 30] — DEFAULT 26 (minimum wage standard, legal baseline). 26 = six-day workweek with one paid rest; 30 = calendar days. Tenant chooses at company onboarding or HR policy screen. Immutable within payroll period once set (to avoid mid-month arithmetic breaks); payroll.leaveTypes: JSON array [{type: 'earned', paidDays: 15, countable: true}, {type: 'sick', paidDays: 12, countable: false}, {type: 'maternity', paidDays: 182, countable: false}] — declares which leave is paid (no LOP) vs unpaid. Some companies may set countable=false for 'earned' to exclude from attendance bonus calculations; payroll.lopAppliedTo: Enum [ABSENT_NO_CALL, ABSENT_APPROVED_LEAVE] — some companies do NOT deduct for rejected leave requests (approved_leave days + company grants paid leave). DEFAULT ABSENT_NO_CALL only. Configurable per tenant; payroll.halfDayThreshold: Int (minutes late) — DEFAULT 15 or 30 min; if arrival > this, mark HALF_DAY automatically. Some companies disable (set to 999) if supervisors mark manually; payroll.proration.includePaidHolidays: Boolean — DEFAULT true. When calculating pro-rata salary on mid-month join/exit, count national holidays as paid (included in numerator). If false, subtract holidays from denominator; payroll.rounding.method: Enum [HALF_UP, HALF_DOWN, TRUNCATE] — DEFAULT HALF_UP per Indian convention (₹2.456 → ₹2.46). Applied to daily rate and final deduction. Immutable per payroll period; payroll.payPeriod: {startDay: 1–31, endDay: 1–31, frequency: 'MONTHLY'} — DEFAULT 1–30 (calendar month). Some companies use 5th-to-4th or 16th-to-15th. Affects which month's attendance falls into which payroll run; payroll.adjustmentApprovalRequired: Boolean — DEFAULT true. Prevents auto-finalization; HR must explicitly approve/reject deduction adjustments before payroll_close executes. FOUNDATIONAL per founder: 'Deductions must be shown as EDITABLE adjustment admin reviews'; payroll.stateName: String — DEFAULT 'MAHARASHTRA' (used to pull state-specific minimum wage if implemented). Stored at company.payrollStateName

**Pitfalls:** IRREVERSIBLE: Choosing wrong baseWorkingDaysPerMonth (26 vs 30) mid-payroll-year. Switching partway through year creates month-to-month deduction inconsistency and audit nightmare. Decision must be made at company onboarding, before first attendance mark. If must change, requires manual recomputation and reconciliation of all prior months.; AUDIT TRAIL LOSS: If deductions are auto-committed to salary (no editable review step), supervisors cannot correct mistakes. Real systems allow edit-before-finalize. AXHY's architecture queues payroll.recompute → HR approves/adjusts → finalize. Skipping the approval step (adjustmentApprovalRequired=false) is only safe if NO human ever makes errors.; PAISE ROUNDING COMPOUNDS: Rounding each day independently then summing differs from rounding the sum. Example: 3 half-days at ₹1,500.00/day = ₹750 × 3 = ₹2,250.00 (truncate 3 daily ÷2 = ₹749.50/each × 3 = ₹2,248.50). Choose once, apply consistently. Document on every payslip.; MID-MONTH JOIN GRACE PERIOD: Minimum Wages Act allows companies to pro-rate first month (employee not entitled to full baseSalaryPaise). Some companies use 26 days as divisor (minimum) even for 20-day work; others use actual 20. Founder must declare: does AXHY allow mid-month joins, and is first month pro-rated or discounted?; HALF-DAY OVER-DEDUCTION: If supervisor marks HALF_DAY + system deducts half-day LOP + employee also took leave request for same day, triple-deduction possible. Service must check: if leave_request for same day → don't auto-deduct, let leave record take precedence.; STATE-SPECIFIC MINIMUM WAGE: 26-day standard is NOT universal. Bihar, Tamil Nadu, and a few states use 22 or 24. If AXHY expands multi-state, tenant must lock their state at onboarding; payroll baseWorkingDaysPerMonth should honor the state rule.; LEAVE WITHOUT APPROVAL AMBIGUITY: If leaveRequest.state = REQUESTED (not yet APPROVED), is the day marked absent LOP or unpaid-wait? Real systems hold pending days out of payroll until approved. AXHY must decide: process attendance immediately (risky if leave gets rejected) or hold Attendance.payDeductPaise = 0 until leave decision, then retroactively apply deduction.; BONUS / INCENTIVE / GRATUITY LINKAGE: If baseSalaryPaise is reduced by LOP, EPF/ESI/gratuity calculations are affected. Documentation for tenants must spell out: LOP reduces all benefits unless company policy explicitly exempts. One company may say 'LOP only deducts wages, not benefits'; another says 'LOP deducts everything.' Must be configurable or at least documented at company level.; CARRY-FORWARD / ENCASHMENT: Some companies allow LOP days to be carried forward or partially paid (rare in cleaning). AXHY assumption: LOP days in month are lost; no carry-forward. If a tenant needs LOP encashment or carry-forward, the data model (Attendance + payDeductPaise per day) cannot easily aggregate. Decision must be explicit.; RETROACTIVE CORRECTIONS: Once payroll_close runs and worker is paid, can deductions be adjusted next month or must a new adjustment row be created? If a supervisor marks an employee ABSENT incorrectly on day 5 but notices on day 25, AXHY allows re-upsert (idempotent on workerId+date). But if payroll already closed, re-upsert fires payroll.recompute → month-2 shows reversal. Audit trail must be clear, or tenant will be confused.

### Flexible Multi-Tenant Payroll Configuration

Real multi-tenant payroll systems succeed by separating stable payroll mechanics from flexible per-company settings using JSONB configuration columns and Maker-Checker approval workflows. ERPNext, Zoho Payroll, and Keka implement configurable salary components (earnings/deductions), pay periods, and LOP calculation rules per company without schema migrations. The pattern: store core payroll tables (members, salary_slips) with tenant_id + organization_id in all keys; keep configuration (salary structure, deduction rules, approval workflows, rounding settings) in a payroll_config JSONB column per organization. India's LOP rules vary by state (no national standard), requiring per-company basis selection (calendar days ÷30 vs working days ÷22). Manual payment is the only option—no payment gateway integration. Approval workflows (Maker-Checker) are mandatory pre-payment, with editable adjustments shown before finalization so admins can see deductions before marking "paid."

**Patterns:** Store payroll configuration as JSONB in a company/organization table: payroll_config with subkeys attendance_deductions_enabled, lop_basis, pay_period, rounding_rule, approval_required, custom_earning_types, custom_deduction_types. Avoids migrations when adding new knobs.; Shared Schema Multi-Tenant: single database, all tables include tenant_id + organization_id as composite partition/distribution key. ERPNext and Zoho use this. Composite keys: PRIMARY KEY(org_id, id), all FK include org_id.; Salary Components are data-driven, not code: Salary Component records define type (earning/deduction), formula, condition, is_flexible, is_statutory. Each org can create custom components without deployment. ERPNext pattern.; Salary Slip stores line items from Salary Structure assignments: earnings[] and deductions[] arrays, each with amount, component_name, formula_result. Attendance data joins to compute LOP per configured basis and deduction_amount.; Maker-Checker before payment: two-step approval (Maker creates salary slip, Checker reviews + edits adjustments before lock), then Admin marks 'paid' with payment_reference (UPI/bank/cash). No auto-payment gateway.; Configuration knobs: attendance_deductions_enabled (bool), lop_calculation_basis (enum: calendar_days|working_days), pay_period (enum: monthly|weekly|biweekly), approval_workflow_enabled (bool), rounding_rule (enum: ceil|floor|nearest), allow_manual_adjustments (bool).; Expansion-safe JSON schema: use nullable JSONB, migrations add new keys with defaults, no NOT NULL constraints on config fields until all orgs migrate. New knob ≈ JSON merge, not ALTER TABLE.; Per-state LOP compliance: store org.state (required in India), payroll_config references state-specific rules. LOP basis depends on Shops & Establishment Act jurisdiction, not one-size-fits-all.; Avoid per-tenant database until 100+ enterprise tenants: Shared Schema scales to 1000s orgs, row-level security via org_id where clauses. Schema per tenant at 10-100 tengs. Dedicated DB only for regulated HIPAA/SOC2 orgs.; Config versioning: keep payroll_config snapshot on each salary slip (salary_slip.config_snapshot JSONB) so audit trails show what rules applied in month X. Never recalculate old slips on config change.

**Config knobs:** attendance_deductions_enabled: boolean. If false, ignore absences entirely; if true, compute LOP daily deductions. Some companies don't want it.; lop_basis: enum (calendar_days|working_days). India has no national standard; depends on Shops & Establishment Act in org's state. Calendar=₹salary/30/day, Working=₹salary/22/day.; pay_period: enum (weekly|biweekly|semimonthly|monthly). Default monthly; affects payroll_entry cadence and fiscal rules.; approval_workflow_enabled: boolean. If true, enforce Maker-Checker before 'paid' mark. If false (rare), admin can mark paid immediately after slip generation.; approval_chain: array of role IDs or user_ids in sequence (e.g. ['hr_role', 'finance_role']), or flat two-stage default (maker, checker).; rounding_rule: enum (ceil|floor|nearest|none). How to round final net pay. Some orgs round to nearest rupee, some to nearest 10, some don't round.; allow_adjustments_after_approval: boolean. If true, admin can edit earnings/deductions after checker approval but before 'paid'. If false, locked after approval.; custom_earning_types: array of earning component names created per org (e.g. 'bonus', 'overtime_pay', 'attendance_incentive'). No code deploy; Salary Component records per org.; custom_deduction_types: array (e.g. 'uniform_cost', 'equipment_damage_recovery', 'fuel_advance'). Again, per-org Salary Component records.; min_base_salary_for_pf: in paise (e.g. 0 for no PF, or 5000000 for ₹50k floor); orgs may exempt low-wage workers from PF.; fiscal_year_start: date (e.g. '2024-04-01' for India FY), used for annual LTA, leave accrual resets.; work_days_per_month: integer (default 22 for India, 26-27 for others). Used for LOP basis=working_days and pro-rata calculations.

**Pitfalls:** NEVER hard-code attendance deductions into Salary Component formulas. Store lop_basis + enabled flag in payroll_config, compute LOP at slip generation time. Recalculating old slips on config change breaks audit trails.; NEVER use per-tenant databases at scale (<100 tenants). Schema drift, migrations cascade, operational nightmare. Shared Schema + org_id is the proven pattern for SaaS payroll.; NEVER skip Maker-Checker approval workflows. Manual payment requires human review. Adjustments must be visible BEFORE payment confirmation, not hidden in background calculations.; NEVER store full salary slip data in a single denormalized JSON column without breaking out earning_lines / deduction_lines. Reporting and audit queries become impossible.; NEVER assume India's LOP rules are national. Each state's Shops & Establishment Act differs. Require org.state in registration; validate LOP config matches state law (hint: no central registry, advise legal review per org).; NEVER allow config changes to retroactively recalculate past salary slips. Snapshot payroll_config on slip generation (config_snapshot JSONB field). If org changes LOP basis in March, Feb slips stay unchanged.; NEVER store payment_reference as free text without validation. Enforce format: UPI IDs (user@bank), bank txn IDs (12-digit alphanumeric), or receipt numbers. Prevents typos that block reconciliation.; NEVER auto-apply adjustments without audit trail. Every line in earning_lines + deduction_lines must have created_by, created_at, reason. Admins must sign off before 'paid'.; NEVER make payroll_config deeply nested (>2 levels). Query performance suffers; JSONB indexes become brittle. Keep it flat: attendance_deductions_enabled, lop_basis, pay_period, etc., not config.attendance.deductions.enabled.; NEVER migrate to Database-per-Tenant unless you have 100+ enterprise customers AND strong compliance requirements. The operational cost (schema versioning, migration orchestration, disaster recovery) is not worth it for SMB SaaS.; NEVER expose approval chain or rounding rules to end-users in UI without explaining consequences. Workers may think deductions are errors if they don't understand LOP basis or rounding logic. Show detailed breakdowns.; NEVER assume 'no payment gateway = no security.' Manual payment still requires: encrypted payment references, audit logs of who marked paid + when, bank reconciliation checks, and theft/embezzlement risk. Admin must be trusted + verified.

### payroll-data-model-lifecycle

A monthly-salary payroll system with manual payment recording requires a robust data model spanning PayRun (company+period), PaySlip (per-worker), and line items (base, deductions, adjustments). The lifecycle is DRAFT (editable, attendance-driven recompute) → APPROVED (locked for human review) → PAID (immutable, irreversible payment recorded with method+reference+timestamp). Immutability is foundational: once PAID, amounts cannot silently recompute; only DRAFT runs recompute when attendance changes. Deductions (especially India LOP — loss-of-pay) must be stored as editable adjustments the admin reviews, not silent auto-deductions. Config-driven fields (pay-period boundaries, rounding, deduction types, company-specific rules) let every tenant adapt the model. Audit events must track every state transition, manual adjustment, and payment recording. Attendance.payDeductPaise stores per-day deductions; these roll into PaySlip totals. The proven pattern: append-only audit trail + immutable ledger entries + conditional updates (only while DRAFT).

**Patterns:** PayRun → PaySlip → LineItem hierarchy: one PayRun per (company, period); N PaySlips per PayRun; M line-items per PaySlip (base salary, each deduction, each adjustment type); Status lifecycle: DRAFT (create, recompute on attendance change, admin edits adjustments) → APPROVED (locked, read-only) → PAID (record payment method + reference + timestamp, then immutable). No retroactive changes once PAID.; Immutability + audit: PAID payroll rows are INSERT-only; corrections require new entries. AuditEvent logs every transition (DRAFT→APPROVED, APPROVED→PAID, manual adjustment). Actor + timestamp + previous-value snapshot on each adjustment.; Recompute idempotency: PaySlip recomputes only while DRAFT, triggered by attendance change (Attendance.status or Attendance.payDeductPaise). Approved/Paid runs never recompute even if attendance is edited later.; Manual adjustments (bonuses, deductions, leave reversals): stored as separate AdjustmentLineItem rows, not merged into base salary. Admin sees line-by-line breakdown; adjustments are editable until APPROVED.; LOP (Loss-of-Pay) handling: Attendance.payDeductPaise is initially 0; payroll recompute fills it based on status (ABSENT_NO_CALL × daily-salary-rate). But it's EDITABLE—admin can override before APPROVED, so company-specific LOP rules (include/exclude weekends, partial deductions) adapt per tenant.; Config-driven knobs: Policy table stores (pay-period type: monthly/bi-weekly, rounding-rule: floor/ceil/nearest, lop-calculation: per-working-day/per-calendar-day, company-deduction-types: [TDS, PF, ESI, custom], adjustment-approval-required: boolean).; Attendance integration: Attendance.payDeductPaise is computed field updated by payroll recompute worker (outbox topic); can be manually edited. PaySlip.lineItems reference Attendance for audit trail.; Payment recording: PaymentRecord table (payRunId, method: cash|upi|bank, reference: txn-id/cheque-no/note, recordedBy, recordedAt, verifiedAt). One per PayRun. Recording is idempotent (upsert, not insert) so admin can correct reference before final reconciliation.; Multi-tenant flexibility: every Membership can have custom baseSalaryPaise; each Company can configure deduction types + LOP rules via Policy. No per-company schema needed; just scoped queries + Policy rows.; Conditional update pattern: payroll recompute uses 'UPDATE PaySlip WHERE status = DRAFT AND (SELECT SUM deduction FROM updated Attendance rows) != current' to prevent concurrent overwrites.; Append-only audit: AuditEvent rows for PAYSLIP_CREATED, PAYSLIP_UPDATED, PAYSLIP_APPROVED, PAYSLIP_PAID, ADJUSTMENT_ADDED, ATTENDANCE_DEDUCTION_UPDATED. Never delete events; corrections create new events.

**Config knobs:** pay_period_type (Policy key payroll.period_type): monthly|bi-weekly|weekly. Affects PayRun boundary calculation. Default: monthly.; lop_calculation_type (payroll.lop_calc): per_working_days|per_calendar_days. If per_working_days, exclude Sundays + public-holidays (via separate Holiday table). If per_calendar_days, use 30-day divisor. Default: per_calendar_days (most common in India).; rounding_rule (payroll.rounding): floor|ceil|nearest_paisa. Applied to net-pay after all deductions. Default: nearest_paisa (to nearest rupee).; deduction_types (payroll.deduction_types): json array. Each company defines which statutory deductions apply: [{type: 'EPF', rate: 0.12, on: 'basic_plus_da'}, {type: 'ESI', rate: 0.0075, on: 'gross', cap: 'yes'}, {type: 'TDS', rate: variable, on: 'gross'}, {type: 'custom_company_levy', amount: 5000}]. Payroll recompute loop iterates these.; attendance_deduction_editable_until (payroll.deduction_edit_deadline_days): int, default 7. After PayRun.createdAt + N days, Attendance.payDeductPaise becomes read-only; HR must create PaySlipLineItem adjustment instead.; approval_required (payroll.requires_approval): boolean, default true. If false, DRAFT → PAID directly (skip APPROVED). Some tenants may not need formal approval.; payment_method_options (payroll.payment_methods): array of {method, label, requires_reference, reference_format}. E.g., [{method: 'bank', label: 'Bank Transfer', requires_reference: true, format: 'UPI_ID|NEFT_REF'}, {method: 'cash', label: 'Cash', requires_reference: false}, {method: 'check', label: 'Check', requires_reference: true, format: 'CHECK_NUMBER'}].; max_batch_size_per_payrun (payroll.batch_size): int, default 500. For large payrolls, chunk PaySlip creation into batches to avoid DB timeout.; salary_display_currency (payroll.display_currency): always INR for India, but allows locale-specific formatting (en-IN with ₹ symbol, paise vs rupee display).; adjustment_categories (payroll.adjustment_types): json array, e.g., [{type: 'bonus', label: 'Performance Bonus', requires_approval: true}, {type: 'loan_deduction', label: 'Loan Repayment', requires_approval: false}, {type: 'leave_reversal', label: 'Leave Reinstated', requires_approval: false}]. Admin picks from this menu when adding adjustments.

**Pitfalls:** FATAL: Allowing PaySlip.baseSalaryPaise to reference live Membership.baseSalaryPaise instead of copying at PayRun creation → if HR edits salary mid-month, old payslips retroactively change. MUST copy at creation; store baseSalaryPaise on each PaySlip immutably.; FATAL: Silently auto-updating Attendance.payDeductPaise after admin approve → breaks audit trail and breaks the immutability promise. Rule: recompute ONLY while PayRun.status=DRAFT. Once APPROVED, even attendance edits don't recompute; admin must create explicit AdjustmentLineItem.; FATAL: Storing LOP as a formula in code (daily_salary × absent_days) instead of storing it as an editable field on Attendance → some companies want to manually override LOP (e.g., 'absent but covered by someone, so no deduction'), and code formula can't adapt. MUST make payDeductPaise editable.; IRREVERSIBLE: Recording a PAID payslip as DRAFT again to 'fix' it → money may have been disbursed; reversing creates a mess. Once PAID, only way to correct is new AdjustmentLineItem (bonus if overpaid, reversal if underpaid) + new payment record. Make PAID terminal.; IRREVERSIBLE: Deleting Attendance or PaySlip rows instead of treating them as immutable → audit trail breaks. Instead, soft-delete (add status=ARCHIVED) and create correction entries.; IRREVERSIBLE: Not recording who approved the payroll (approvedBy, approvedAt) → when payroll is disputed, no one can prove who signed off. MUST log Membership.userId (the HR who approved) at DRAFT→APPROVED transition.; DATA INTEGRITY: Recomputing payroll without locking the Attendance table → supervisor edits attendance while payroll recompute is running, causing race condition. Use pessimistic lock (SELECT ... FOR UPDATE) or conditional-update-on-version.; DATA INTEGRITY: Storing payDeductPaise in Attendance but also duplicating it in PaySlipLineItem without a back-reference → when admin updates Attendance.payDeductPaise, PaySlipLineItem doesn't update, creating mismatch. MUST have sourceId (FK to Attendance) or versioning.; COMPLIANCE DRIFT: Hardcoding EPF rate (12%) instead of reading from Policy → when India raises statutory rate, code breaks and you need a deploy. MUST store rates in Policy and read dynamically.; COMPLIANCE DRIFT: Using Membership.baseSalaryPaise as the deduction base for LOP without checking if basic salary changed during the pay period → if salary increased mid-month and employee was absent, which salary do you use? MUST define per-policy (pro-rata? full month old rate? full month new rate?).; PERFORMANCE: Computing PaySlip totals (base - deductions + adjustments) on every query instead of storing netPayPaise → with 5000 workers, 12 pay-periods/year, scanning PaySlipLineItem to sum each time is slow. MUST denormalize (store netPayPaise, totalDeductionsPaise, totalAdjustmentsPaise on PaySlip) and maintain invariant via trigger or recompute-once.; PAYMENT TRACKING: Not idempotenting PaymentRecord.create → if the 'record payment' API is retried, two payment records are created, payment shows as double. MUST use (payRunId) unique constraint + upsert, or idempotent-token pattern.; MANUAL PAYMENT PITFALL: Recording payment reference without storing payment date + disbursement date separately → tax authorities later ask 'when did you actually pay', and you only have 'when we recorded it' which is not the same. MUST store disbursedAt separately from recordedAt.; MULTI-TENANT: Scoping PayRun only by companyId, not by HRPod or company location → some large companies want separate payroll runs per pod/location. MUST allow podId as optional scoping dimension.; AUDIT TRAIL: Logging 'PAYSLIP_UPDATED' but not logging what changed → auditor can't reconstruct state history. MUST log previousValue + newValue in AuditEvent.payload for every mutable field.; RECOMPUTE SEMANTICS: Using outbox topic payroll.recompute without idempotency key → if the message is processed twice, payroll is recomputed twice and may end up in an inconsistent state (e.g., two identical line items). MUST use message deduplication (based on workerId + payRunId + event-timestamp).
