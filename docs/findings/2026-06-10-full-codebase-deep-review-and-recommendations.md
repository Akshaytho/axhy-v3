## 0. Verdict in one paragraph

The codebase is production-grade in most places that matter: strict DB-verified auth with token epochs and rotation-with-compromise-detection, atomic apply transactions in chat, an outbox with multi-replica claim leases, real AI cost ceilings, a disk-persisted offline upload queue, and server-side role gates in admin-web. The blocker is not missing features — it is that **the RLS activation plan in `handoff/NEXT_SESSION.md` does not match the code**: the read paths and the in-process dispatcher use bare prisma with no GUC, so flipping `DATABASE_URL` to `axhy_app` per the runbook would blank every worker/supervisor dashboard and silently kill AI photo verification. Resolve that one architecture decision, close four ops gaps (OTA updates, API versioning, a restore drill, Sentry), fix three small correctness bugs, and this product is ready for pilot customer #1.

## 1. BLOCKER — RLS activation gap (handoff overstates readiness)

**Claim in NEXT_SESSION.md:** "App is `axhy_app`-ready; only the founder's prod connection switch remains." Runbook step 3: "Flip the API service DATABASE_URL → axhy_app. Dispatcher/worker stays on `postgres`."

**What the code actually does (all verified):**

- Migration `packages/shared-schema/prisma/migrations/20260609_023_rls_tenant_isolation/migration.sql` (lines 86-104) puts `ENABLE` + `FORCE ROW LEVEL SECURITY` and a `tenant_isolation` policy on 27 tables including `Worker`, `Visit`, `Site`, `Assignment`, `LivingDoc`, `SupervisorDecision`, `HRUpdate`, `VisitPhoto`. With the GUC unset, the policy predicate is NULL → **zero rows visible, all writes rejected** (fail-closed, stated at migration lines 11-13).
- Migration `20260609_024_rls_auth_self_read/migration.sql` adds `tenant_self_read` ONLY on `Membership` + `Worker`, and only when `axhy.current_user_id` is set (lines 34-46).
- `apps/backend/src/lib/prisma.ts` is a plain PrismaClient — no global extension injects any GUC.

**Read paths that pass bare prisma (no GUC) into services that query FORCE-RLS tables:**

The "tenant-exempt" / "these tables have no RLS" comments in those files (e.g. `worker-today.ts:21-22`) were written **before** migration 023 and are now stale.

**The dispatcher half (bigger):** `handleAiVerify` reads/writes `Visit` + `VisitPhoto` with bare prisma (`dispatcher/handlers/ai.ts:111` findFirst, `:463` $transaction, `:468,478` updateMany — no GUC anywhere). The dispatcher runs **in-process inside the API** (`server.ts:281`, `RUN_DISPATCHER_IN_PROCESS` defaults to true; there is no separately deployed dispatcher service in `railway.json`). So "dispatcher stays on postgres" is impossible as written — flipping the API role flips the dispatcher with it → every submitted visit stays `AWAITING_VERIFICATION` forever. Same bare-prisma pattern in `dispatcher/handlers/notifications.ts:122,131,233,296` (AuditEvent read is RLS'd; Notification create would be rejected).

**Why nothing is broken today:** prod connects as `postgres`, which bypasses RLS unconditionally (migration 023 comment, lines 15-19). The lab RLS suites (15/15) tested the policies and specific wrapped paths — not these routes under `axhy_app`.

**Decision required (founder):**

- **Option A — make the flip real:** wrap every bare read in `withTenantRead`/`withUserContext` (cost: loses the parallel-connection latency win those comments fought for; /supervisor/today was 12s cold under a tx per its own comment), AND deploy the dispatcher as a separate Railway service on the `postgres` role with `RUN_DISPATCHER_IN_PROCESS=false` on the API.
- **Option B — don't flip:** keep the app on `postgres`; app-level `companyId` filters remain the primary isolation (they are consistently present); RLS becomes defense-in-depth that only engages where GUCs are already set. Honest, shippable, but INVARIANT 1 "DB-enforced" stays aspirational and migration 023's FORCE RLS gives false comfort.
- Either is defensible. Flipping per the current runbook without choosing is the only wrong move.

## 2. Launch blockers (besides §1)

1. **No mobile update path.** `apps/mobile/eas.json` builds APKs, internal distribution; `expo-updates` is not in `apps/mobile/package.json`. Field APKs can only be fixed by manual reinstall.
2. **No API versioning.** All routes register bare paths (`server.ts:215-253`) — `/chat/messages`, not `/v1/chat/messages`. Combined with #1: one breaking backend change strands every installed client with no remediation path. Add `/v1` prefix + EAS Update channel **before** APKs ship.
3. **Restore is untested** _(corrected after verification — original claim "no backup tooling" was wrong)_. Backup tooling exists and has run: `apps/backend/scripts/backup-db.sh` (pg_dump → gzip at line 28, 14-day retention prune at line 37, restore instructions in comments at lines 33-34; names Railway managed backups as primary), a 75MB prod dump from 2026-06-06 exists locally (`backups/axhy-prod-20260606-004312.sql.gz`), and `scripts/setup-railway.md` §6 (lines 68-72) covers verifying Railway daily backups with 7-day retention. What's missing is the half that matters in an incident: **no evidence a restore has ever been performed**, and restore steps live only as script comments. Do one full restore drill into a scratch DB and write down what happened. Untested restores = unknown backups.
4. **Rotate `JWT_SECRET`** (already in NEXT_SESSION — prod still has the guessable dev placeholder; `lib/jwt.ts:20` requires ≥32 chars).

## 8. Growth / "world domination" recommendations (grounded in what exists)

The two moats from the master plan are already real in code — they are not features to add, they are compounding loops to start:

- **Margin moat:** AI only at the input boundary with enforced ceilings — `assertWithinBudget` WARN/CAP + idempotent owner alerts (`packages/ai-tools/src/model-policy.ts:183-247`), atomic spend increments (`cost-tracking.ts:42-59`), per-supervisor daily token caps checked before the AI call (`chat.ts:768-777`), ai.verify hard ₹1/call ceiling (`handlers/ai.ts:61`). Competitors quoting AI-heavy ops platforms cannot match this cost structure.
- **Switching-cost moat:** per-supervisor LivingDoc with 100-rule cap + auto-expiry + version-bumped prompt cache (`chat.ts:1943-2071`), semantic turn retrieval (pgvector), 6-tier prompt composition. Every month of usage makes the assistant smarter about that specific company — and worthless to a competitor.

Both moats compound **only after launch**. So the #1 growth recommendation is the same as the #1 release recommendation: ship the pilot. Then, in leverage order:

1. **Client-side photo compression (M2)** — cheapest material improvement for actual users; the dependency is already installed.
2. **WhatsApp two-way notifications** — workers already authenticate over WhatsApp (`lib/whatsapp-otp.ts`); the outbox already enqueues `worker.leave_approved`, `swap.accepted`, etc. (gupshup handlers currently log). Delivering decisions to workers on the channel they already use closes the operational loop and is visible value the owner can see day 1.
3. **Owner trust dashboard** — the data already exists (AI verdicts + fraud_probability per visit in `Visit.verificationText/verificationModel` + `VisitPhoto.aiVerifyStatus`, complaint trends per site, attendance). Surfacing it in `/owner` makes the AI's value visible instead of silent, and is the demo that sells customer #2-10.
4. **Leave/swap/complaint state machines (C8/ledger #20)** — pays down the duplicated lifecycle logic before it drifts.
5. **Pilot instrumentation** — with Sentry (O1) + the existing audit events, define the 5 numbers to watch in week 1: visits submitted/day, % auto-VERIFIED vs FLAGGED, OTP delivery success, chat messages/supervisor/day, AI ₹/tenant/day. The `ai_cost_daily` view groundwork already exists (`ChatMessage.costInr/cacheTokens`).
6. **Deferred-by-design list stays deferred:** vector RAG expansion, WhatsApp Business API, TTS, multi-region, MCP server (at 15 tenants) — per master plan, do not pull these forward.
